## 结论

此前十场景测试使用空模型库，`ai_status=not_configured`，没有覆盖工坊的真实 AI 提取、评审和修复。本次已接入主库 `model_configs.id=1`（`deepseek-flash`，roles 含 `workshop`）真实补跑。

**正式补跑 3 个模型场景，AI 提取 3/3 成功；完整评审 1/3 成功，2/3 在评审或修复阶段失败。**

- 通用时钟失锁：提取 + 评审完整成功，质量分 74，最终因 E1 未验证停在 `needs_confirmation`。
- 光模块 RX 功率异常：提取成功，评审成功并发现 2 个 error 级规则问题；随后修复调用失败，质量回退到确定性结果，最终因 E1、E2 未验证停在 `needs_confirmation`。
- USB FLASH 写保护：提取成功，评审连续 3 次 `IncompleteRead` 失败；质量分 70，最终因 E1–E3 未验证停在 `needs_confirmation`。

**额外 5 次大输入/资料不完整探测均未完成 AI 提取**，全部回退到确定性规则：看门狗完整资料 3 次失败、紧凑资料 1 次失败、资料不完整 1 次失败。失败原因集中为 HTTP 503、`IncompleteRead` 和模型未返回合法 JSON。

三条正式场景都没有发布技能。原因是工坊的证据门禁要求真实正例/反例确认规则，而本次只验证模型链路，没有提供真实日志样本；这不是 AI 失败，也不应为了跑通而绕过门禁。

|---|---:|---|---|---|---:|
| 通用时钟失锁 | 22.27s | 成功，7.140s，输入 5,354 / 输出 1,498 | 成功，14.748s，输入 4,584 / 输出 2,831 | `needs_confirmation`，E1 未验证 | 74 |

| USB FLASH 写保护 | 134.61s | 成功，15.741s，输入 15,184 / 输出 3,453 | 连续 3 次 `IncompleteRead`，未完成 | `needs_confirmation`，E1–E3 未验证 | 70 |

### 1. 通用时钟失锁（完整成功）

- 草稿：`bbu-fault-clock-loss-of-lock`
- `ai_status=success`，`source=ai`，`model=deepseek-flash`
- 提取和评审各一次成功，`attempts` 记录了完整的两条调用
- AI 评审提出 4 个 warning，包括：
  - `LOCKED=0` 没有词边界，`NOTLOCKED=0`、`UNLOCKED=0` 可能误命中；
  - E1 只证明“失锁”现象，不能直接证明“参考源丢失”根因；
  - 缺少正例/反例，规则无法验证；
  - 没有定义恢复状态的判定口径。
- 最终 `check=False`，未验证规则 `["E1"]`，停在人工确认，未发布。

### 2. 光模块 RX 功率异常（提取 + 评审成功，修复失败）

- 草稿：`bbu-fault-optical-rx-power-low`
- `ai_status=success`，`source=ai`，`model=deepseek-flash`
- 提取：`RX_POWER` 阈值、`optical.log`、根因和恢复条件均生成
- 评审发现 2 个 error：
  - `any_of` 正则丢失 `RX_POWER\\s*=` 前缀，可能在整行任意位置匹配负数，导致跨字段误判；
  - 阈值原文是“低于 -18”，但 `-1[89](\\\\.\\\\d+)?` 会命中 `-18`、`-18.0`，边界不一致。
- 评审还发现 `LOS` 裸词会匹配 `CLOSE`/`LOSS`，且 E2 没有被根因条件引用。
- 评审后进入修复调用，修复请求失败：HTTP 503 + 模型未返回合法 JSON。
- 修复失败后代码把 `quality` 重新设为确定性 `audit_spec` 结果，评审发现的 error 没有保留到最终质量对象；本次 `quality.ok=true`、分数 76，只是因为 `check=False` 才仍停在人工确认。
- 这是一个需要单独修复的回退缺陷：评审已经发现 error，后续修复失败时不应丢掉评审结论，否则在证据已确认的场景可能被误放行。

### 3. USB FLASH 写保护（提取成功，评审失败）

- 草稿：`bbu-fault-vsw-usbflash`
- `ai_status=success`，`source=ai`，`model=deepseek-flash`
- 提取成功：15,184 input tokens / 3,453 output tokens，规则 E1–E3 生成
- 评审连续 3 次 `IncompleteRead`，`analysis.notes` 记录“AI 评审/修复未完成”
- `attempts` 只有 extract 一条，评审失败的 token 没有统计
- 质量分 70，`check=False`，未验证 E1–E3，停在人工确认

## 失败探测

| 探测 | 耗时 | 失败表现 | 回退结果 |
|---|---:|---|---|
| 看门狗完整资料（首次） | 98.75s | 3 次 `IncompleteRead` | 确定性 E1–E4，质量 64，`check=False` |
| 看门狗完整资料（`max_tokens=4096`） | 74.58s | HTTP 503 + `IncompleteRead` + JSON 非法 | 确定性 E1–E4，质量 64，`check=False` |
| 看门狗紧凑资料（显式配方） | 56.2s | HTTP 503 + JSON 非法 | 确定性 E1/E3/E4，质量 64，`check=False` |
| 资料不完整 | 39.14s | HTTP 503 + JSON 非法 | 0 条规则，质量 26，`quality.ok=False`，构建在质量阶段阻断 |
| 看门狗 + `model_schema_mode=off` | 41.42s | 仅 JSON 非法 | 确定性 E1/E3/E4；说明不是 strict JSON Schema 单独导致 |

这些失败都有确定性回退，平台没有把回退结果标成 AI 生成；资料不完整场景也正确阻断了构建。但失败调用没有进入 `attempts`，所以报告只能看到错误文本，不能统计失败 token。

## 发现的问题

1. **失败调用不计入调用统计**  
   `WorkshopService._generate` 的 `record()` 只在 `gateway.complete()` 成功后追加 `attempts`；`gateway.complete()` 最终失败时不返回 usage，导致 HTTP 503/IncompleteRead/JSON 失败的 token 全部丢失。当前报告中的 token 只是成功调用的统计。

2. **`ai_status=success` 语义过宽**  
   它只表示“提取成功”，不表示“评审成功”。USB 场景提取成功、评审完全失败，仍然是 `ai_status=success`；评审失败只写在 `analysis.notes`。前端/后续调用方如果只看 `ai_status`，会误以为完整 AI 链路成功。

3. **评审 error 在修复失败时被覆盖**  
   `bbu/workshop.py` 的异常分支执行 `quality = audit_spec(spec)`；如果评审已经返回 error，随后修复调用失败，评审 error 会被确定性审计结果覆盖。建议改为：已有 `review` 时保留 `_merge_review` 的结果，只补一条“修复未完成”的说明；没有评审结果时才重置为 `audit_spec`。

4. **模型端点不稳定，且无法从错误文本区分根因**  
   同一模型短通用场景可以完整成功，配方/大输入场景出现 503、IncompleteRead、JSON 非法；降低 `max_tokens=4096`、只重试 1 次、关闭 schema 模式都没有消除。当前不能断定是模型服务瞬断、输出截断、上下文过长还是模型 JSON 输出能力问题，因为 `AIGateway` 没有保留原始响应。

5. **评审输出负载偏大**  
   USB 提取 15,184 input tokens 后，评审要再读完整 spec + source context；光模块评审输出 4,048 tokens。对 `deepseek-flash` 这类端点，评审阶段容易触发长响应中断。建议评审只输出问题列表和分数，不要求重复完整 spec；修复只对 error 级问题触发一次。

6. **证据门禁按预期生效**  
   三个正式场景全部 `check=False`，未验证 E1–E3 被正确列为待确认；资料不完整场景 `quality.ok=False`。这说明 AI 生成不能绕过规则验证和构建门禁。

## 建议

1. 先修复“评审 error 被修复失败覆盖”的回退缺陷，并补一个 fake gateway 回归测试：评审返回 error → 修复抛异常 → 最终 `quality.ok` 必须为 false，且 error 保留。
2. 为工坊单独配置稳定模型：优先使用可用性更好的模型别名/MaaS 端点；`workshop` 角色与诊断/报告角色分开，避免同一端点波动影响工坊。
3. 降低评审负载：评审提示词只传摘要 spec + 原文摘录，输出限制为 `issues/questions/score`；大配方先提取、后分段评审，不要一次塞入完整 spec。
4. 增加调用失败审计：记录 `{stage, model, latency_ms, http_status, error_type}`；如果响应带 usage，也记录失败 usage；没有 usage 时至少记录估算 token，避免统计缺口。
5. 把 `ai_status` 拆成 `extract_status`、`review_status`、`repair_status`，或在 UI 显示“提取成功 / 评审未完成”的部分成功状态。
6. 保留当前证据门禁：AI 评审只能发现和收紧规则，不能替代真实日志正例/反例；未验证规则继续阻断构建和发布。
