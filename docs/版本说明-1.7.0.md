# BBU 故障诊断平台 1.7.0 版本说明（R5 真实数据成熟度）

发布日期：2026-11-25  
版本：`1.7.0`  
数据库 schema：`7`  
基线：`1.6.0`（schema 6）→ `1.7.0`（schema 7）

## 1. 本阶段目标与边界

R5 的目标是把真实案例从“能导入”推进到“可分配、可复核、可版本化、可评测、可审计”，并用质量门禁约束对外口径。本阶段不伪造现场根因：没有 ground truth 的案例继续保持 `unlabeled`，不进入准确率统计，也不宣称现网准确率。

本阶段未改变用户既有约束：

- 不开放公开注册；
- 不实现联网自动更新；
- 主 Web 进程不自我提权；
- 网页升级仍只能通过独立 root/systemd 助手调用固定脚本。

## 2. 数据库变更（schema 6 → 7）

`real_cases` 新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `reviewer_id` | INTEGER | 分配的复核专家用户 ID，可空 |
| `review_status` | TEXT | `unassigned` / `pending` / `confirmed` / `rejected`，默认 `unassigned` |
| `assigned_at` | TEXT | 分配时间，ISO 8601 UTC |

新增 `case_label_history`：

| 字段 | 说明 |
|---|---|
| `id` | 自增主键 |
| `case_id` | 案例 ID |
| `actor_id` / `actor_name` | 操作者 |
| `action` | `assign` / `unassign` / `label` / `approve` / `reject` / `correct` |
| `old_json` / `new_json` | 变更前后快照，JSON |
| `note` | 备注 |
| `created_at` | 操作时间 |

迁移逻辑在 `bbu/db.py` 中完成；旧库启动时自动补列、建索引并把 `schema_version` 更新为 `7`。案例 `case.json` 与数据库保持同步写入，历史记录只增不改。

## 3. 后端能力

### 3.1 案例队列与权限

`GET /api/cases` 支持：

- `split`：`unlabeled/dev/test/hidden/train/all`
- `status`：`unlabeled/labeled/golden/deprecated/all`
- `review_status`：`unassigned/pending/confirmed/rejected/all`
- `assigned=me`：只查看分配给当前账号的案例

权限规则：

- 管理员：查看全部案例，可分配复核人；
- reviewer：默认只看分配给自己的案例；
- engineer：只看自己录入或没有创建者的案例；
- 案例详情、历史、标签接口复用同一套可见性判断。

### 3.2 复核分配

`POST /api/cases/{id}/assign-reviewer`

- 仅管理员可调用；
- 复核人必须是 `active` 状态的 `reviewer` 或 `admin`；
- `reviewer_id=0` 表示取消分配；
- 分配后写站内通知 `case_assigned`，并在 `case_label_history` 记录 `assign`；
- 审计动作 `case.assign`。

### 3.3 标签与复核闭环

`POST /api/cases/{id}/label` 在原接口上扩展：

- `expected_roots` / `excluded_roots`：期望根因、显式排除根因；
- `split` / `status`：数据集切分与案例状态；
- `labels.evidence_window`：证据时间窗 `start/end`；
- `labels.recovery_result`：`已恢复/未恢复/间歇恢复/未验证`；
- `decision_note`：复核说明；
- `action`：`label` / `approve` / `reject` / `correct`；
- `review_status`：显式指定复核状态。

约束：

- `labeled/golden` 至少要有期望根因或排除根因；
- `golden` 必须切分到 `dev/test/hidden`，不能停留在 `unlabeled`；
- 创建者可以补录标签，但只有被分配的复核人或管理员可以确认/退回；
- 每次变更写 `case_label_history` 和审计 `case.label`，不覆盖旧版本。

`GET /api/cases/{id}/history` 返回按时间倒序的标签与分配历史。

### 3.4 评测入口

`POST /api/evaluations/run`

- 仅管理员 + CSRF；
- `split` 只接受 `dev/test/hidden`；
- `limit=0` 表示该切分全部案例；
- 复用 `EvaluationService`，关闭 LLM 与自学习，保持确定性；
- 返回评测 ID、summary、逐案例结果和报告路径；
- 审计动作 `evaluation.run`。

评测摘要保留 `exact_rate`、precision、recall、F1、误报率、拒判率、置信度校准和“样本不足不得对外宣称”的限制说明。

### 3.5 质量门禁

`GET /api/quality` 增加：

- `case_review`：未分配/待复核/已复核/已退回数量；
- `real_cases`：已标注、golden、test、未标注数量。

原门禁不变：

- 已复核真实任务 ≥ 30；
- golden 真实案例 ≥ 20；
- 独立 test 案例 ≥ 10；
- 真实评测 exact_rate ≥ 0.8。

四项全部通过才把 `ready_for_real_data` 置为 `true`。

### 3.6 无描述真实日志的路由弱信号

现场采集包经常只有日志、没有故障描述。R5 在规划前把以下信息作为弱信号：

- `inventory.detected_hints`（`clockstatuslog`、`gnss`、`ocxo`、`alarm` 等）；
- 压缩包顶层成员文件名；
- 技能规则中的 `any_of/contains/tokens` 签名。

弱信号只参与路由打分，仍要求技能规则在日志内容中命中；不会仅凭文件名直接判根因。无匹配技能时保持 `needs_data`。

## 4. 前端变更

新增 `web/assets/js/page_cases.js` 和 `#/cases` 路由：

- 案例列表：复核状态筛选、待复核/已复核/golden 统计、复核人列；
- 案例详情：现场信息、输入文件、数据指纹、当前标签快照；
- 根因标注表单：期望/排除根因、证据时间窗、恢复结果、案例状态、切分、复核备注；
- 操作：保存标签、确认复核、退回/拒判；
- 标签历史时间线：操作者、动作、备注、变更后状态；
- 管理员分配/调整复核人；
- 管理员运行评测：选择切分、限制数量、展示 exact/误报/拒判结果与报告路径。

导航与工作台：

- 管理员/工程师导航新增“真实案例”；
- reviewer 导航新增“真实案例”；
- 工作台 reviewer 提示同时显示待复核任务与待复核案例；
- 成熟度卡片增加“案例复核”和真实案例 golden/test 计数，链接到案例页。

## 6. 真实数据现状（重要）

截至本版本发布，主库 `data/bbu.db`：

| 指标 | 当前值 |
|---|---|
| schema | 7 |
| 真实案例总数 | 3 |
| `unlabeled` | 3 |
| `labeled` | 0 |
| `golden` | 0 |
| `test/hidden` | 0 |
| 案例复核 | 未分配 3 / 待复核 0 / 已复核 0 / 已退回 0 |
| 已复核真实任务 | 0 |
| 最近真实评测 | 无 |
| `ready_for_real_data` | **false** |

三个案例保持未标注：

- `C-ba49bb1a2d` / `shunhe-6323-20250519`
- `C-e3d5790949` / `6321-20251230`
- `C-9481dc8c59` / `6321-20260525`

原因：现有资料没有经过现场确认的 ground truth。R5 交付的是标注、复核、版本化和评测能力，不是替现场专家猜根因。未复核案例不会进入准确率，也不会计入 golden/test 门禁。

门禁当前：

- 已复核真实任务：0 / 30；
- golden 真实案例：0 / 20；
- 独立测试集案例：0 / 10；
- 真实评测 exact_rate：无评测，按 0 处理；
- `ready_for_real_data=false`。

因此本版本只能报告“合成回归通过 + 真实样本覆盖 3 例（未标注）”，不能宣称现网准确率。

## 7. 离线包与升级

离线包：`dist/bbu-fault-platform-1.7.0-offline.tar.gz`  
SHA256：见 `dist/bbu-fault-platform-1.7.0-offline.tar.gz.sha256`（随包分发，避免文档内自引用）

升级路径：`1.6.0`（schema 6）→ `1.7.0`（schema 7）。升级脚本会先备份数据库和 `STATE_DIR`，再切换 release；`--with-state` 回滚可恢复到 1.6.0/schema 6。网页升级仍由 root/systemd 助手执行固定脚本，主 Web 不自我提权。

真实离线升级演练（手工 `--no-service` 模式，目录 `/tmp/bbu-r5-upgrade2`）：

| 步骤 | 结果 |
|---|---|
| 安装 1.6.0 | 健康检查 `v1.6.0`，schema 6 |
| 1.6.0 → 1.7.0 升级 | 健康检查 `v1.7.0`，schema 7，`case_label_history` 表存在 |
| `--with-state` 回滚 | 回到 `v1.6.0` / schema 6，`rollback-safety` 目录保留回滚时点数据 |
| 再次升级 1.7.0 | 回到 `v1.7.0` / schema 7 |

演练期间因首次使用 `--skip-backup` 无法可靠回滚，已改用带完整快照的干净环境重跑；最终结论以 `/tmp/bbu-r5-upgrade2` 为准。该演练不包含 root/systemd 单元安装。

本容器限制：当前 `uid=1234`、`systemctl is-system-running=offline`，无法真实安装 root/systemd 单元；R4 的 root 助手仍只通过 fake helper 验证 Web 状态机与 UI，真实服务器 dogfood 未在本容器执行。R5 未改变该限制。

## 8. 升级后验收建议

1. 用管理员登录，进入“真实案例”，确认 3 个案例可见且为“未分配/待复核”状态；
2. 给 reviewer 分配 1 个案例，确认 reviewer 只看到分配给自己的案例，并收到站内通知；
3. reviewer 填写期望/排除根因、证据时间窗、恢复结果，保存后查看历史版本；
4. 管理员确认复核后，把案例切到 `test`，运行评测，检查 exact/误报/拒判和报告；
5. 检查 `/api/quality` 的 `real_cases`、`case_review` 和 `maturity_gate`，确认 `ready_for_real_data` 仍为 false，直到真实数据达到门禁。

## 9. 已知限制

- 真实案例只有 3 个且无现场确认根因，无法达到 30/20/10/0.8 门禁；
- 现有技能库主要覆盖 VSW/示例故障，现场 BBU 采集包可能无匹配技能，平台会保持 `needs_data` 而不是强行给结论；
- 评测为同步执行，大样本会占用请求时间；后续可改为后台任务；
- root/systemd 助手未在真实服务器安装验证；
- 案例分配目前由管理员发起，reviewer 不能自行领取未分配案例。
