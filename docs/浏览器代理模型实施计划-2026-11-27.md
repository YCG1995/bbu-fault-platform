## 1. 背景与已确认口径

现场部署形态：平台服务端在无外网（或无法直连模型网关）的网段，运维人员的浏览器可以经系统代理访问模型网关。服务端出站这条路不通，浏览器这条路通。

已确认的三条口径：

1. **Key 对普通用户不可见。** 共享模型由管理员配置并保存 Key，普通用户只能在页面上看到模型名称与执行位置，Key 只在调用执行的瞬间由服务端注入到请求里，用户界面、日志、轨迹、导出包中均不出现明文。
2. **浏览器代理模型参与自动调度。** 与其它全局模型一起按 `roles` + `priority` 排序竞争，用户不需要手动切换；用户浏览器不在线时自动跳过并落到服务端模型。
3. **提供一个自检页。** 能在现场 3 分钟内判定：代理是否可达、CORS 预检是否放行、混合内容是否被拦、认证头是否匹配、目标网关协议是否兼容。

一句话概括方案：**语义在服务端，传输在浏览器。** 服务端仍然负责构造请求、解析响应、Schema 校验、修复、回退、预算与审计；浏览器只做一次 `fetch` 并把原始响应回传。

## 2. 目标与非目标

### 2.1 目标

- 管理员可创建"浏览器代理执行"的共享模型，配置项与服务端模型一致（含 Key）。
- 任意授权用户的浏览器可承接该模型的调用，多个用户互不干扰。
- 调度、失败回退、预算、审计、Schema 校验与现有服务端模型完全一致。
- Key 不出现在任何普通用户可见界面与日志中。
- 现场可自助诊断连通性。

### 2.2 非目标

- 不做本地 relay 桌面程序（CORS 不可用时的备选方案，另立计划）。
- 不支持浏览器端流式输出（后台任务只需要最终文本，助手流式留到后续版本）。
- 不支持定时任务、离线评测、MCP 调用依赖浏览器模型（这些没有活跃浏览器）。
- 不做跨进程/多实例中继（当前是单进程 `ThreadingHTTPServer`，内存队列足够）。

## 3. 总体架构

```text
┌──────────────────────────── 服务端（单进程） ────────────────────────────┐
│                                                                        │
│  AIGateway.complete()                                                  │
│    └─ choose(role)  ──(过滤：无在线浏览器则剔除 browser 模型)           │
│         └─ _call(model)                                                │
│              └─ _call_openai() 构造 url/payload/headers                │
│                   └─ transport=server → _post_json()  （现状，不变）    │
│                   └─ transport=browser → RelayHub.submit()             │
│                                              │                         │
│  RelayHub（bbu/relay.py，内存 + Condition）  │                         │
│    ├─ windows: user_id → {window_id, last_seen}                        │
│    ├─ pending: call_id → RelayCall(pending/claimed/done/expired)       │
│    └─ submit() 阻塞等待结果，超时抛 RelayAbsentError                    │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ HTTP（平台自身会话，Cookie 鉴权）
┌──────────────────────────────────▼─────────────────────────────────────┐
│  用户浏览器（页面常驻 relay.js）                                        │
│    GET /api/relay/status   5s 心跳 + 是否有待执行调用                    │
│    GET /api/relay/calls    长轮询领任务（含本次调用的 Key）              │
│    fetch(url, spec)        走浏览器系统代理 / PAC                       │
│    POST .../result         回传 status + body_text                      │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ 系统代理（HTTP/HTTPS/PAC）
                            模型网关（OpenAI 兼容 / Anthropic）
```

三条数据流要分开看：

- **配置流**：管理员 → `model_configs.extra` → 模型列表页。
- **执行流**：worker 线程 → RelayHub → 浏览器 → 网关 → 回传 → 原解析链路。
- **回退流**：租约不存在/认领超时/执行超时 → 记 `relay_absent` → 下一个模型 → 全失败则业务降级。

## 5. 接口设计

### 5.1 总表

| 方法 | 路径 | 鉴权 | 用途 |
|---|---|---|---|
| GET | `/api/relay/status` | 登录用户 + CSRF 关闭 | 心跳、查询可承接模型与待执行数 |
| GET | `/api/relay/calls` | 登录用户 | 长轮询领取一个调用 |
| POST | `/api/relay/calls/{call_id}/result` | 登录用户 + CSRF | 回传执行结果 |
| POST | `/api/models/{id}/relay-test` | 管理员 | 发起一次浏览器内自检 |
| GET | `/api/models/{id}/relay-test/{test_id}` | 管理员 | 查询自检结果 |
| GET | `/relay-check.html` | 免登录 | 静态自检页 |

路由注册位置：`bbu/api.py` 的 `r.add(...)` 段，模型相关接口集中在 `505–510` 行附近。

### 5.2 契约

**GET /api/relay/status**

```json
// 200
{
  "enabled": true,
  "window": {"window_id": "w-8f3a", "ttl_sec": 120, "windows": 1},
  "poll_sec": 5,
  "pending": 1,
  "models": [
    {"id": 7, "name": "内网 MaaS（浏览器）", "model": "deepseek-v4-flash",
     "roles": ["default", "workshop"], "priority": 0, "max_concurrent": 2}
  ]
}
```

`pending > 0` 时前端才进入领取循环；`models` 为空时前端不启动中继。

**GET /api/relay/calls?window_id=&wait=10**

- `204 No Content`：等待期内无任务，前端立即再轮询一次。
- `200`：返回一条调用。

```json
{
  "call_id": "c-2b7c9e14",
  "model_id": 7,
  "model_name": "内网 MaaS（浏览器）",
  "purpose": "workshop.review",
  "method": "POST",
  "url": "https://maas.corp.example/v1/chat/completions",
  "headers": {"Content-Type": "application/json", "Accept": "application/json"},
  "body": "{\"model\":\"deepseek-v4-flash\",\"messages\":[...]}",
  "auth": {"header": "Authorization", "value": "Bearer sk-****"},
  "timeout_sec": 90,
  "max_bytes": 1048576,
  "expires_at": "2026-11-27T10:12:31+08:00"
}
```

约束：

- 响应头 `Cache-Control: no-store`、`Pragma: no-cache`，禁止任何中间层缓存。
- `auth` 与 `headers` 分离，便于日志/轨迹统一脱敏；`headers` 中永不出现 Key。
- 每条调用 `call_id` 单次消费：第二次领取同一 `call_id` 返回 `409`。
- 只返回 `user_id` 与当前会话匹配的调用；跨用户领取返回 `403` 并写审计。

**POST /api/relay/calls/{call_id}/result**

```json
{"status": 200, "body_text": "{...}", "latency_ms": 1832,
 "error_kind": "", "truncated": false}
```

- `body_text` ≤ `relay_max_response_bytes`，超出返回 `413` 并按失败处理。
- 幂等：同一 `call_id` 重复提交返回 `409`，服务端只采用第一次。
- 过期调用返回 `410`。
- `error_kind` 取 `network|abort|timeout|http`，用于区分回退语义。

### 5.3 服务端与浏览器的传输契约

服务端只下发**已经序列化好的** `body` 字符串与 `headers`，浏览器不做任何协议拼装、不改 body、不加头（除 `auth`）。这样所有协议细节、Schema、提示词都留在服务端，浏览器只是哑传输，后续换协议不需要动前端。

## 6. 服务端模块 `bbu/relay.py`

### 6.1 数据结构与状态机

```text
RelayWindow: user_id, window_id, last_seen, active_calls
RelayCall:   call_id, user_id, model_id, spec, state, created_at, claimed_at,
             deadline, result, error
state: pending → claimed → done | failed | expired | cancelled
```

- 队列按 `user_id` 分组，同组内 FIFO；不同用户互不阻塞。
- 单用户可领取的窗口：`relay_max_windows_per_user` 内均可领，先到先得。

### 6.2 关键方法

```python
class RelayHub:
    def __init__(self, db, config): ...
    def register_window(self, user_id: int, window_id: str) -> dict
    def online(self, user_id: int) -> bool
    def available_models(self, user_id: int) -> list[dict]
    def submit(self, user_id, model, spec, *, purpose, claim_timeout, exec_timeout) -> RelayResult
    def claim(self, user_id, window_id, wait_sec) -> RelayCall | None
    def complete(self, user_id, call_id, status, body_text, latency_ms, error_kind) -> None
    def cancel_user(self, user_id) -> int      # 退出登录/会话撤销时清理
```

`submit()` 用 `threading.Condition` 等待，返回三种结果：成功（含 usage 解析原料）、客户端缺席（`RelayAbsentError`）、执行失败（`RelayExecError`，带 HTTP 状态）。

### 6.3 并发与线程占用

- 每个等待中的模型调用占用 1 个 worker 线程，上限就是 `worker.max_workers`，不额外开线程。
- 长轮询每窗口占用 1 个 HTTP 线程（`ThreadingHTTPServer` 每连接一线程），`wait=10` 秒，50 人规模约 50 连接，可接受；超过 100 人再考虑改 SSE。
- `max_concurrent` 只限制浏览器侧并行 `fetch` 数，服务端队列不设上限但受预算（`max_llm_calls`）约束。

### 6.4 清理

- 后台清理线程每 5 秒扫一遍：`claimed` 超过 `deadline` → `expired`；`pending` 超过 `claim_timeout` → `failed(relay_absent)`。
- 窗口心跳超 `relay_lease_ttl_sec` → 标记离线，其名下 `pending` 立即失败（不等到 claim_timeout）。
- 用户登出、会话撤销、服务重启 → 清空该用户队列。

### 6.5 与 `ai.py` 的契约

```python
@dataclass
class RelayResult:
    text: str
    usage: Usage
    status: int
    latency_ms: int
```

`ai.py` 只依赖 `submit()`，不感知队列细节。

## 7. `bbu/ai.py` 改造

### 7.1 传输分支

改 `_call_openai`（`bbu/ai.py:1618` 起）与 `_call_anthropic`：构造完 `url/payload/headers` 后，按 `model.get("transport")` 分叉。

```python
if transport == "browser":
    result = self.relay.submit(user_id, model, RelaySpec(
        url=url, method="POST", headers=_strip_auth(headers),
        body=json.dumps(payload, ensure_ascii=False),
        auth=_auth_of(headers), timeout_sec=model["timeout_sec"],
    ), purpose=purpose)
    data = _parse_openai_payload(json.loads(result.text))   # 复用现有解析
```

要点：

- **强制非流式**：`payload["stream"] = False`，浏览器不解析 SSE。
- 响应解析、错误映射、`response_format` 降级重试全部复用现有函数，不复制逻辑。
- 浏览器回传的 HTTP 状态按现有规则映射：`429/5xx` 可重试，`401/400/413` 不可重试。

### 7.2 `choose()` 过滤

`AIGateway` 增加 `relay` 引用（`bbu/api.py:297` 构造处传入；`bbu/evaluation.py:383/614` 传 `None`）。

```python
def _models(self, user_id=None):
    rows = ([personal] if personal else []) + self._global_models()
    rows = [m for m in rows if self._usable_here(m, user_id)]
    return rows

def _usable_here(self, model, user_id):
    if model.get("transport") != "browser":
        return True
    if not self.relay or not self.relay.online(user_id):
        return False                      # 无在线窗口：直接剔除，不产生等待
    return self.relay.role_allowed(model, user_id)
```

剔除后该模型不参与排序，也不写失败计数——离线不是模型故障。

### 7.3 熔断隔离

`AIError` 增加 `kind` 字段，新增两类：

| kind | 触发 | 是否计传输熔断 | 是否计 Schema 熔断 |
|---|---|---|---|
| `relay_absent` | 无窗口/认领超时/窗口掉线 | 否 | 否 |
| `relay_exec_failed` | 浏览器返回网络错误、abort、超时 | 否 | 否 |
| HTTP 401/429/5xx | 浏览器回传真实状态 | 按现有规则 | 按现有规则 |

实现点：`complete()` 里 `breaker.fail()` 前判断 `exc.kind not in RELAY_CLIENT_KINDS`。

### 7.4 用量与审计

- `usage.record()` 增加 `transport` 字段（`personal`/`global` 之外的第三维）。
- `audit_logs.detail_json` 记录 `{model_id, call_id, window_id, client_ip, bytes, latency_ms}`，**不记 prompt、不记 Key**。
- 异常才写审计：`relay_claim_timeout`、`relay_cross_user_claim`、`relay_result_oversize`。正常调用只写 usage，避免审计膨胀。

### 7.5 测试与发现接口

- `test_model()`（`ai.py:1302` 附近）对 browser 模型不再走服务端，改为 §9.5 的管理端自检。
- `list_models()`（`ai.py:1479`）对 browser 模型由浏览器执行：自检页与管理端「获取模型」按钮都走浏览器 `GET /models`，服务端只提供保存后的 Key 注入，不代发。

## 8. 前端改造

### 8.1 `web/assets/js/relay.js`（新增，约 180 行）

状态机：

```text
idle ──(status.models 非空)──► heartbeat
heartbeat ──(pending>0)──► claim
claim ──(200 spec)──► execute ──► submit result ──► claim
claim ──(204)──► claim（继续长轮询）
任意失败 ──(指数退避 2/4/8s，上限 30s)──► heartbeat
页面卸载 ──► beacon 释放窗口
```

- `window_id`：`sessionStorage` 生成一次，窗口内固定；`pagehide` 时 `navigator.sendBeacon` 通知释放。
- 执行：`AbortController` + `timeout_sec`；读取 `Content-Length` 提前拒绝超限；`res.text()` 后再次校验长度。
- 403/409/410 分别处理：跨用户（理论上不会出现）→ 停止并提示；重复领取 → 忽略；过期 → 丢弃。
- 页面隐藏超过 5 分钟仍继续心跳（浏览器会节流 `setTimeout`，允许漏拍，服务端按 TTL 判定）。

### 8.2 多窗口与并发

- 同一用户多窗口都心跳，谁先领谁执行；`max_concurrent` 是单窗口上限，单用户总并发由 `relay_max_windows_per_user × max_concurrent` 决定。
- 顶掉最旧窗口时，旧窗口下次心跳收到 `409 window_evicted`，停止轮询并提示"另一个窗口已接管浏览器代理"。

### 8.3 URL 黑名单（浏览器侧）

在 `relay.js` 里再拦一次，防止管理员误配或恶意配置把用户浏览器当内网探测器：

- 拒绝 `127.0.0.1`、`localhost`、`[::1]`、`169.254.*`、`fe80::/10`；
- 只允许 `https`，除非平台本身是 http 且模型地址为明确放行的内网 http（由 `relay_enabled_http` 控制，默认 false）；
- 拒绝 `file:`、`data:`、`javascript:`。

### 8.4 状态提示

- 顶栏模型状态条增加一枚徽标：`浏览器代理 运行中 / 未连接`，点击打开自检页。
- 模型下拉（若有）对 browser 模型标注「浏览器执行」。
- 任务详情/工坊页增加一行提示："本次 AI 环节由你的浏览器执行，请保持本页打开"。

| 1 | 页面环境 | 读 `location.protocol`、`origin`、UA | — | — |
| 2 | 混合内容 | https 页面 + http 目标 | 不触发 | 平台是 https，模型必须是 https |
| 3 | 网络可达（不判 CORS） | `fetch(url, {mode:'no-cors'})` | 返回 opaque 且无异常 | 代理/路由/证书问题，打开 DevTools 看 `net::ERR_*` |
| 4 | CORS 预检 | `fetch(url, {headers:{Authorization}})` | `res.type === 'cors'` 且非 `TypeError` | 网关需允许平台 Origin 与 `authorization,content-type` |
| 5 | 模型列表 | `GET {base}/models` | 200 + 数组 | 地址或 Key 不匹配 |
| 6 | 最小推理 | `POST` 8 tokens，内容"只回复 OK" | 200 + `choices[0]` | 协议不兼容 |
| 7 | 认证样式 | 依次试 `Bearer` / `api-key` / `x-api-key`+`anthropic-version` | 任一通过 | 输出可用的那一种，供管理端参考 |
| 8 | 私网访问（PNA） | 目标为私网地址时的预检结果 | 通过 | Chrome 需要网关回 `Access-Control-Allow-Private-Network: true` |
| 9 | 代理特征 | 对比 `no-cors` 与 `cors` 两种结果 | 记录 | 两者都失败＝网络；只有 cors 失败＝CORS |
| 10 | 报告导出 | 生成 JSON（不含 Key） | — | — |

### 9.3 关键实现：区分"代理不通"和"CORS 拒绝"

浏览器 JS 拿不到 `net::ERR_PROXY_CONNECTION_FAILED` 这类细节，两种失败都表现为 `TypeError: Failed to fetch`。唯一可行的区分手段是 `no-cors` 探测：

- `mode:'no-cors'` 成功返回 opaque → 网络层通，问题在 CORS；
- `mode:'no-cors'` 也失败 → 代理、DNS、证书或路由问题。

页面必须把这条结论原样展示，避免现场把 CORS 问题误判成代理问题。详细错误码仍需看 DevTools Network 面板，页面给出操作指引。

### 9.5 管理端「浏览器内自检」

- `POST /api/models/{id}/relay-test` 由服务端往该管理员用户的队列里投一条 `purpose=test` 的合成调用，复用真实 relay 路径（含 Key 注入），**Key 不出现在任何响应里**。

## 10. 安全设计

### 10.1 Key 生命周期

| 阶段 | 位置 | 约束 |
|---|---|---|
| 保存 | `model_configs.api_key`，`secret_box` 加密 | 与现状一致 |
| 下发 | 仅 `GET /api/relay/calls` 的 200 响应，字段 `auth.value` | `no-store`、单次、仅匹配用户 |
| 使用 | 浏览器内存变量，`fetch` 后立即置空 | 不写 `localStorage`、不写 `sessionStorage` |
| 审计 | 只记 `sha256(key)[:8]` 指纹 | 禁止明文 |

禁止项（要写进代码注释与测试断言）：

- 禁止 Key 出现在 URL 查询串、`console.log`、toast、错误信息、任务轨迹、导出包、前端状态树。
- 禁止把整条 `spec` 落盘；如需排障，只落 `call_id` 与 `url host/path`。
- 前端任何异常上报都走白名单字段，不上报 `auth`。

### 10.2 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 共享 Key 被有权限用户提取 | 可脱离平台直接调用 | 专用低配额 Key、定期轮换、`allow_roles` 限制、按用户审计用量 |
| 管理员误配内网地址 | 用户浏览器被当探测器 | 服务端与浏览器双重黑名单 |
| XSS 窃取注入的 Key | 单次调用窗口内泄露 | CSP 收紧、依赖自审、Key 内存即用即清 |
| 跨用户领取 | 他人任务被代执行 | `user_id` 强绑定 + 审计 + 403 |
| 回传伪造结果 | 假模型输出 | 结果按不可信输入处理，仍过 Schema/claim 校验，模型本就无裁决权 |

### 10.3 权限

- 只有管理员能创建/修改 browser 模型。
- 普通用户只能看到 `models` 列表中的名称与执行位置，看不到 Key、看不到 base_url 完整地址（可显示 host）。
- `allow_roles` 非空时，非授权角色既看不到也领不到该模型。

## 11. 调度与降级

| 场景 | 行为 | 用户可见 |
|---|---|---|
| 无浏览器在线 | `choose()` 直接剔除 browser 模型 | 无提示 |
| 有在线但 10s 未认领 | `relay_absent`，切下一模型 | 任务日志一行"浏览器代理未响应，已切换模型" |
| 浏览器执行超时 | `relay_absent`，切下一模型 | 同上 |
| 浏览器返回 429 | 按现行 429 策略切备用模型 | 现有提示不变 |
| 浏览器返回 401 | 不重试，切下一模型 | "模型 Key 无效" |
| 全部模型失败 | 业务层降级（诊断走规则、工坊跳过 AI 审查） | 现有降级文案 |
| 用户关页/切走 | 租约 120s 后判离线，在途调用立即失败 | 任务页提示"请保持页面打开" |

优先级建议：同档 priority 内，browser 模型排在服务端模型之后（`_round_robin_priority` 之后追加一层 transport 排序），避免用户无感知地把任务压在自己的标签页上。

## 14. 风险与回滚

| 风险 | 概率 | 影响 | 处置 |
|---|---|---|---|
| 目标网关不给 CORS 头 | 中 | 方案不可用 | 先跑自检页；确认不可行则转本地 relay 方案 |
| 系统代理 bypass 目标域名 | 中 | 请求直连失败 | 部署前由 IT 核对 PAC |
| 企业代理需认证 | 低 | 首次请求 407 | 浏览器先访问一次触发认证 |
| 混合内容 | 中 | https 页面调 http 被拦 | 强制 https 或平台降 http（不推荐） |
| 后台标签页节流 | 高 | 心跳漏拍，任务切模型 | TTL 120s + 页面提示；关键任务建议前台执行 |
| 长轮询占线程 | 低 | 高并发时线程压力 | `wait=10`，超 100 人改 SSE |

回滚：`relay_enabled=false` 一键关闭；已建 browser 模型自动降级为不可用并被跳过，不影响服务端模型链路；schema 23 的 `transport` 列对旧版本无影响，可直接回退 1.28.2（列存在但被忽略）。

## 附录 B：关键代码骨架

```python
# bbu/relay.py
RELAY_CLIENT_KINDS = ("relay_absent", "relay_exec_failed")

class RelayHub:
    def submit(self, user_id, model, spec, *, purpose, claim_timeout, exec_timeout):
        call = self._enqueue(user_id, model, spec, purpose, claim_timeout, exec_timeout)
        with self._cv:
            deadline = time.time() + claim_timeout + exec_timeout
            while call.state in ("pending", "claimed"):
                remain = deadline - time.time()
                if remain <= 0:
                    self._expire(call)
                    raise AIError("浏览器代理未响应", kind="relay_absent", retryable=False)
                self._cv.wait(min(remain, 1.0))
        if call.state == "done":
            return call.result
        raise AIError(call.error or "浏览器代理执行失败", kind="relay_exec_failed",
                      retryable=False)
```

async function tick() {
  const st = await api('/api/relay/status?window_id=' + windowId, { csrf: false });
  if (!st.models.length) return schedule(30000);
  if (st.pending > 0) await claimLoop();
  else schedule(st.poll_sec * 1000);
}

async function claimLoop() {
  while (running) {
    const call = await api(`/api/relay/calls?window_id=${windowId}&wait=10`, { csrf: false });

## 附录 C：现场必须先确认的 4 件事

1. 目标网关是否回 `Access-Control-Allow-Origin`（含预检允许 `authorization, content-type`）。
