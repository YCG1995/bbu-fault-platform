# 部署手册（完全离线）

> 初次部署推荐使用“一键部署包”：包内已带 CPython 运行时，目标机不需要预装 Python。详见 [`一键部署说明.md`](一键部署说明.md)。本手册的源码安装方式适用于研发环境和自定义部署。

## 1. 环境要求

- Linux x86_64/ARM64，推荐 4 vCPU / 8 GB 内存 / 100 GB 磁盘（日志规模大时按实际增加）。
- Python **3.12**（最低 3.11）；不需要 pip、Node、Nginx 或任何外网访问。
- 系统工具：`bash`、`tar`、`systemctl`（root 安装时）。`curl` 非必需。
- 内网端口：默认 `8080`（可改）；如需域名/HTTPS，前面可放单位现有反向代理。

检查 Python：

```bash
python3 -V
python3 -c "import sqlite3, ssl; print('ok')"
```

平台只用标准库；PyYAML 已随包放在 `vendor/yaml`，不要在现场执行 `pip install`。

## 2. 生成离线包（在有源码的机器上）

```bash
cd bbu-fault-platform
bash deploy/make_release.sh
```

产物：

```text
dist/bbu-fault-platform-1.19.2-offline.tar.gz
dist/bbu-fault-platform-1.19.2-offline.tar.gz.sha256
```

打包会排除 `data/`、`skills/`、`cases/`、`config.json`、`__pycache__` 与测试产生的数据，不会把管理员密码或 API Key 带进发布包。

## 3. 内网服务器安装

```bash
sha256sum -c bbu-fault-platform-1.19.2-offline.tar.gz.sha256
tar -xzf bbu-fault-platform-1.19.2-offline.tar.gz
sudo bash bbu-fault-platform/deploy/install_offline.sh --port 8080
```

常用参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--prefix` | `/opt/bbu-fault-platform` | 程序目录（代码只读） |
| `--state-dir` | `/var/lib/bbu-fault-platform` | 数据/技能/案例目录（可写） |
| `--host` | `0.0.0.0` | 监听地址；仅本机反代可设 `127.0.0.1` |
| `--port` | `8080` | 监听端口 |
| `--user` | `bbu` | 运行系统账号，不存在时创建 |
| `--no-service` | 否 | 不安装 systemd，只落盘并初始化 |
| `--force` | 否 | 首次安装或修复时覆盖已有 `config.json`；**不能用于版本升级** |

安装脚本会：

1. 检查 Python 与 vendor PyYAML；
2. 创建系统用户与数据目录；
3. 复制程序到 `--prefix`，生成绝对路径的 `config.json`；
4. 以服务用户执行 `run.py --init-only`，创建 SQLite 库、目录与初始管理员；
5. 安装并启动 `bbu-fault-platform.service`；
6. 轮询 `/api/health` 确认服务可用。

安装完成后查看初始密码：

```bash
sudo cat /var/lib/bbu-fault-platform/data/初始管理员密码.txt
sudo systemctl status bbu-fault-platform
sudo journalctl -u bbu-fault-platform -n 100 --no-pager
```

浏览器访问 `http://<服务器IP>:8080/`，用户名 `admin`，首次登录必须改密。改密后可删除初始密码文件。

## 4. 服务管理

```bash
sudo systemctl start bbu-fault-platform
sudo systemctl stop bbu-fault-platform
sudo systemctl restart bbu-fault-platform
sudo systemctl status bbu-fault-platform
sudo journalctl -u bbu-fault-platform -f
```

systemd 单元要点：

- `User=bbu`，`WorkingDirectory=/opt/bbu-fault-platform`
- `ProtectSystem=strict`、`PrivateTmp=true`；**不要设置 `NoNewPrivileges=true`**，否则受限 sudo 升级助手无法启动（详见 1.20.2 版本说明）
- 初始 `ReadWritePaths=/var/lib/bbu-fault-platform`；网页切换工作目录成功后，root 助手会同时改写 `BBU_DATA_DIR/BBU_SKILLS_DIR/BBU_CASES_DIR` 与这一行到新目录
- `Restart=on-failure`，异常退出自动拉起
- 运行数据标准布局为 `<state-dir>/{data,skills,cases,updates,backups}`；`/etc/bbu-upgrade.json` 的 `allowed_work_roots` 限制网页可切换的目标根目录

## 5. 防火墙与网络

只开放服务端口给办公网/运维网：

```bash
sudo firewall-cmd --permanent --add-port=8080/tcp
sudo firewall-cmd --reload
```

不要把 8080 直接暴露到互联网。若需要 HTTPS，使用单位现有 Nginx/Apache 反向代理：

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_buffering off;          # SSE 必须关闭缓冲
    proxy_read_timeout 3000s;     # 覆盖任务超时 2400s
    client_max_body_size 2048m;   # 与 max_upload_mb 对齐
}
```

若反代在另一台机器，安装时用 `--host 127.0.0.1`，只让本机反代访问。

## 5.1 MCP 与悬浮助手

MCP 和悬浮助手复用平台现有的 HTTP 服务，不需要额外端口或守护进程。

### 开关与限流

| 配置键 | 默认 | 环境变量 | 说明 |
| --- | --- | --- | --- |
| `assistant_enabled` | `true` | `BBU_ASSISTANT_ENABLED` | 关闭后悬浮窗隐藏，助手 API 返回 404 |
| `assistant_rate_per_min` | `12` | `BBU_ASSISTANT_RATE_PER_MIN` | 每用户每分钟助手请求上限 |
| `mcp_allow_remote` | `false` | `BBU_MCP_ALLOW_REMOTE` | 默认仅本机 loopback |

配置可写入 `config.json`，也可由 systemd `Environment=` 注入。修改后重启服务。

### MCP 端点与安全

- 端点：`POST /mcp`；`GET /mcp` 返回 405；不支持 SSE。
- 鉴权：`Authorization: Bearer <token>` 或 `X-MCP-Token`。
- Token 在「系统信息 → MCP / 助手」生成；只显示一次，数据库只存 SHA-256。
- 默认只接受本机请求。若平台在反向代理后，代理可能改变对端 IP；没有明确需要时不要开启 `mcp_allow_remote`，也不要把 `/mcp` 暴露到公网。
- Token 绑定创建它的管理员账号；账号停用、轮换或撤销后立即失效。
- 普通用户只读自己的通知/任务事件；管理员 MCP read 可读系统状态和审计；admin 模式只额外放行低风险写工具，升级/回滚、用户/模型变更永不通过 MCP 执行。

### 客户端配置

```json
{
  "mcpServers": {
    "bbu-faultscope": {
      "type": "http",
      "url": "http://127.0.0.1:8080/mcp",
      "headers": { "Authorization": "Bearer <YOUR_TOKEN>" }
    }
  }
}
```

建议先用 `read` 模式联调；确认客户端可信后再按需生成 `admin` Token。

### 外部 IM

外部 IM 当前只提供可插拔适配器，默认读取 `data/external_messages.json`，不连接真实飞书/豆包。该文件只读，不支持消息回写；真实 provider 接入前需确认凭据、出域授权和用户身份映射。

## 6. AI 模型接入

登录后「模型接入 → 添加模型」：

- OpenAI 兼容：Base URL 到 `/v1` 结尾，如 `http://oneapi.internal/v1`；模型名填网关实际模型 ID。
- Anthropic：Base URL `https://api.anthropic.com`（或内网代理地址），协议选 Anthropic。
- 完全离线且无内网模型时，不配置模型即可；平台自动走确定性路径。
- 角色可多选：`default`、`planner`、`router`、`arbiter`、`writer`、`workshop`。`planner` 生成动态波次计划；`router` 仅作为老部署的规划回退。保存后可用「测试连通」验证；失败不影响确定性诊断。
- 完全离线且无内网模型时，不配置模型即可；平台自动走「确定性波次」：按规则分并行执行候选技能，仍会生成报告。
- 每个任务最多调用 planner 1 次、补规划 1 次、仲裁 1 次、报告 1 次；任务级 `max_llm_calls`、`max_total_tokens`、`task_timeout_sec` 仍然生效。
- 成功任务会自动创建工坊「自学习」草稿，但绝不自动发布；管理员需在工坊确认规则并构建/发布。若不需要，将 `config.json` 的 `auto_distill` 设为 `false`。

API Key 加密存储在 SQLite，密钥文件为 `/var/lib/bbu-fault-platform/data/master.key`（`0600`）。备份时必须同时备份 `data/`，否则换机后 Key 无法解密。

### 规划相关配置

`config.json` 可调整：

```json
{
  "planner_enabled": true,
  "planner_replan": true,
  "planner_max_steps": 4,
  "planner_max_total_skills": 8,
  "planner_replan_max_skills": 4,
  "auto_distill": true
}
```

- `planner_enabled=false`：即使配置了 planner 也不生成 AI 计划，只用确定性波次。
- `planner_replan=false`：关闭补规划，首轮执行后直接仲裁。
- `planner_max_steps` / `planner_max_total_skills`：计划硬上限，超出由 `normalize_plan()` 确定性裁剪。
- `auto_distill=false`：关闭成功任务自动创建工坊草稿；已创建的草稿不受影响。

计划门槛固定为 `always`、`previous_unmatched`、`previous_conflict`、`previous_low_confidence`、`previous_gap`，首步强制 `always`。

## 7. 数据备份与恢复

备份脚本会先用 SQLite Backup API 生成一致性快照，再打包数据、技能与案例。默认排除原始上传文件、案例输入、解压目录和运行临时目录；报告、证据、技能与案例定义仍保留：

```bash
sudo bash /opt/bbu-fault-platform/deploy/backup.sh \
  --state-dir /var/lib/bbu-fault-platform \
  --out /backup/bbu-$(date +%F).tar.gz
```

恢复到新机器：

```bash
sudo systemctl stop bbu-fault-platform
sudo tar -xzf /backup/bbu-2026-11-24.tar.gz -C /var/lib/bbu-fault-platform
sudo chown -R bbu:bbu /var/lib/bbu-fault-platform
sudo systemctl start bbu-fault-platform
```

注意：

- 备份包含 `data/master.key` 与数据库，属于敏感文件，按密钥介质管理。
- 不要只备份 `bbu.db` 而忽略 `master.key`，否则模型 Key 不可用。
- 默认不包含 `data/uploads`、`data/tasks/*/skills/*/unpacked`、`data/workshop/*/logs`、`data/workshop/*/extracted`、`data/real_logs`、`data/real_cases*/*/input` 和 `cases/*/*/input`。恢复后历史报告可直接查看，但这些任务/案例要重跑时需重新上传原始日志。
- 恢复后浏览器需重新登录（会话仍在数据库内，但建议强制改密）。

## 8. 升级与回滚

**已部署实例不要使用 `install_offline.sh --force` 升级。** 新发布包提供独立升级入口，自动备份、保留配置、迁移数据库、重启并校验版本：

```bash
sha256sum -c bbu-fault-platform-1.19.2-offline.tar.gz.sha256
mkdir -p /tmp/bbu-release-1.19.2
tar -xzf bbu-fault-platform-1.19.2-offline.tar.gz -C /tmp/bbu-release-1.19.2
sudo bash /tmp/bbu-release-1.19.2/bbu-fault-platform/deploy/upgrade_offline.sh
```

默认保留 `/var/lib/bbu-fault-platform` 中的数据库、密钥、上传、技能、案例和复核记录，也保留 `/opt/bbu-fault-platform/config.json`。升级快照保存在 `/var/lib/bbu-fault-platform/backups/`。

完整回滚：

```bash
sudo bash /opt/bbu-fault-platform/deploy/rollback_offline.sh \
  --backup /var/lib/bbu-fault-platform/backups/<升级快照目录> \
  --with-state
```

自定义路径、无 systemd 部署、健康检查和数据恢复注意事项见 `docs/升级与回滚.md`。

## 9. 常见问题

**启动失败：端口被占用**

```bash
ss -ltnp | grep ':8080'
sudo systemctl status bbu-fault-platform
```

改端口：编辑 `/opt/bbu-fault-platform/config.json` 的 `port`，或改 systemd `ExecStart` 后 `daemon-reload`。

**页面 401 / 登录后立即退出**

检查服务器时间是否准确；Cookie 为 `SameSite=Strict`，确认访问域名与反代 Host 一致。清空浏览器 Cookie 后重试。

**上传大日志失败**

同时检查：

- 平台 `config.json` 的 `max_upload_mb`（默认 2048）
- 反向代理 `client_max_body_size`
- 磁盘剩余空间与 `max_extract_mb`（默认 8192）

**技能显示“不可用 / incompatible”**

该技能缺少 `scripts/run_analysis.py`、`assets/fault-profile.yaml` 等关键组件。用元 Skill 重新构建，或修正技能包后重新导入；平台不会强行执行不完整技能。

**AI 一直超时或费用不可控**

检查模型配置的 `timeout_sec` 与角色优先级；平台每任务硬限制 `max_llm_calls=12`、`max_total_tokens=200000`、`task_timeout_sec=2400`，超限自动回退确定性路径。若仍异常，先停用该模型配置，确认确定性链路正常。

**数据库损坏**

停止服务，保留现场后从最近备份恢复；不要在生产库上直接 `sqlite3 .recover` 覆盖原文件。SQLite 使用 WAL，复制时需同时处理 `-wal/-shm`，推荐使用 `deploy/backup.sh`。
