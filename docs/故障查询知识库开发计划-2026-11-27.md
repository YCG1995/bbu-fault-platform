# 故障查询知识库开发计划

> 基线：BBU FaultScope `1.28.2` / 数据库 schema `23` / 工具层 20 个工具  
> 计划日期：2026-11-27  
> 目标版本：`1.29.0`（检索内核与问答）→ `1.30.0`（知识库管理与多格式导入）→ `1.31.0`（召回与质量闭环）  
> 实施对象：`bbu-fault-platform`，继续遵守“零第三方 Python 依赖、离线可部署、单标准离线包”的既有约束。

## 0. 结论摘要

1. **先做检索内核，再做界面。** 故障知识库的价值取决于“问一句话能不能找到对的案例”，不是上传页面。计划把一半以上的工程量放在数据模型、分词、索引、多路召回和评测上，界面按既有原生 JS 规范补齐。
2. **纯标准库可以达到很高的召回。** 我用附件中的 2268 条真实问答做了原型验证：紧凑倒排索引构建 1.54 秒、常驻内存 57.9 MB、平均查询 11.7 ms；同题检索 Recall@5 = 100%，去掉板卡/版本后的症状检索 Recall@5 = 99.29%，原因句检索 Recall@5 = 95.75%。这证明不需要向量库或 jieba 也能达到可用水平。
3. **“完美召回”要用工程定义收口。** 目标按查询类型分层：实体精确查询（板卡+告警/版本+故障词）Recall@1 = 100%；症状描述类 Recall@5 ≥ 99.5%；开放改写/口语/跨术语类 Recall@5 ≥ 97%、Recall@10 ≥ 99%；总体 Recall@5 ≥ 99%。无答案查询必须明确拒答且可解释。上线前用 300 条专家金标准验收，不以“感觉准”代替指标。
4. **知识库以“案例”为检索单元，不以整条 CSV 行为单元。** 样例中有 396 条记录包含两个及以上【原因分析】块（原单 + 转交/派生），必须拆成多条案例；否则一个根因会被另一条根因的长文本稀释，引用也无法落到具体处置。
5. **三个入口共用一套内核：**
   - 新页面“故障知识库”提供对话窗口（`#/kb`）与管理窗口；
   - 统一工具层新增 `search_fault_kb`、`get_fault_case`，悬浮助手与 MCP 直接可用；
   - 诊断任务在规划阶段引用相似历史案例，报告增加“历史参考”附录；技能工坊可检索参考案例，但不自动采纳结论。
6. **排期：** 1 名全栈约 24 个工作日（含 P0 可行性 2 天、P4 发布 3 天）。`1.29.0` 在 7 个工作日内形成可用闭环；`1.30.0` 补齐管理与多格式；`1.31.0` 做金标准、调优和 10k 容量验证。发布仍只交付一个标准离线包。

### 1.3 硬约束

- **零第三方依赖**：不引入 numpy、jieba、whoosh、langchain、向量数据库、PDF 解析库、OCR 引擎；PyYAML 仍只作为现有 vendor 保留，知识库不使用。
- **离线与老系统**：目标机可能无外网、无 systemd、glibc 2.17（Ubuntu 16.04），运行时是随包内置的 CPython。所有新代码必须是纯 Python，不依赖 C 扩展。
- **单机单库**：v1 只建一个默认知识库（`kb_id=1` 预留），不引入多租户、多库路由、分布式索引。
- **数据不能随包分发**：附件 CSV 含姓名+工号，4 MB 真实数据不进入离线包；包内只放 20 条脱敏样例供自测。
- **不改变既有诊断语义**：历史案例只作为参考，不得替代当前日志证据，不得直接改变根因仲裁。
- **UI 一致性**：继续用原生 JS + 既有 CSS 变量、`mount` 页面骨架、`data-act` 事件绑定；不引入组件库。

### 1.4 本期不做

- 多知识库、跨库联邦检索、知识图谱推理；
- 本地 OCR 引擎、扫描 PDF 的版面还原；
- 互联网抓取、自动生成故障案例、自动写回诊断报告；
- 向量语义检索作为必选链路（仅保留可选通道）；
- 问答流式输出（先非流式，后续再评估 SSE）；
- 中英互译、多语言知识库。

## 2. 数据资产与知识模型

### 2.1 附件 CSV 实测

| 指标 | 实测值 |
|---|---:|
| 记录数 | 2268 条 |
| 字段 | `question`、`answer` 两列，UTF-8 BOM |
| 文件大小 | 4,050,795 字节 |
| 总字符量 | 1,814,508 字 |
| 问题长度 | 中位数 41 字，最长 224 字 |
| 答案长度 | 中位数 660 字，最长 7287 字，均值 754 字 |
| 每条答案小节数 | 平均 13.7 个（模板化【】小节） |
| 含【原因分析】 | 2342 处；2081 条有“原因描述” |
| 多根因记录 | 396 条含 2 个及以上【原因分析】块 |
| 含 7–8 位连续数字 | 1921 条（大量为“姓名+工号”，如 `孙哲10262951`） |
| 完全重复问题 / 答案 | 9 条 / 2 条 |
| 高频同名标题 | 52 条为“woody系统在数据集的站点上发现故障,请处理” |
| 板卡型号 | 问题中可识别 20 种（VBPE2/VBPE3/VBPD2/VSWD1 等），正文出现更广 |

四个直接影响设计的结论：

1. **标题不能作为唯一索引字段。** 52 条标题完全相同、9 条问题重复；只索引 `question` 会把大量无关案例排到前面。必须把 `answer` 拆成现象、原因、方案三类字段参与评分。
2. **一条记录可能对应多个故障结论。** 396 条记录含“原单原因 + 转交/派生原因”，必须拆成案例级单元，否则回答只能引用其中一段，且排名会被长文本拉低。
3. **PII 必须在索引前处理。** 1921 条含工号样式；默认将姓名/工号/电话/邮箱替换为占位符，原文只对管理员开放。
4. **模板标签需要归一化。** 实际标签有 `【2.是否其它变更引入】`、`【*3.原因描述】`、`【处理方案】`、`【*处理方案】` 等变体，不能按字符串精确匹配；需要“去序号、去星号、别名映射”的规范化表。

### 2.2 三层知识模型

```text
一次导入 / 一个文件
  └─ kb_documents（文档：来源、标题、原文、附件、状态、质量分）
       └─ kb_cases（案例：1 条可检索的故障结论，1..N 个）
            └─ kb_sections（逻辑小节：存于 kb_cases.sections_json，展示/引用用）
```

- **文档层**负责来源追溯、权限、版本、附件、去重；一条 CSV 记录、一个 DOCX、一张截图都可以是一篇文档。
- **案例层**是检索与引用单元。一个文档可拆出多条案例（多根因、多个转交结论），每条案例有自己的现象、原因、方案、板卡、标签、质量分。
- **小节层**负责展示与精确摘录；检索命中案例后，引用定位到具体小节，避免把 7000 字原文整段塞给模型。

### 2.3 统一字段与小节规范

| 规范字段 | 来源（CSV 样例） | 说明 |
|---|---|---|
| `title` / `title_clean` | `question` | 原文标题保留；`title_clean` 去掉版本前缀、`[标签]`、`(史诗故事验收)` 等噪声 |
| `symptom` | 【详细描述】+【实际结果】+ 标题 | 现象主字段，权重最高 |
| `environment` | 【测试环境：】 | 制式、版本、组网、站点 |
| `expected` / `actual` | 【预期结果：】/【实际结果：】 | 用于区分“现象”与“差异” |
| `repro` | 【现象是否可以复现：】 | 偶现/必现/概率 |
| `found_date` / `location` | 【发现日期：】/【发生地点：】 | 时间、地点元数据 |
| `cause` / `cause_detail` | 【原因分析】+【*3.原因描述】 | 根因摘要 + 详细分析 |
| `solution` | 【*处理方案】/【解决方案】/【修改建议】 | 处置步骤 |
| `prevention` | 【故障建议】/【变更影响分析】 | 预防与影响，可选 |
| `boards` | 标题+正文正则 | 规范化为大写型号：`VBPe2→VBPE2`、`VSWd1→VSWD1` |
| `domains` | 标题前缀 `[电源][时钟][存储]…` | 领域标签，用于筛选与加权 |
| `versions` | `V4.30.20.00B219-1` 等 | 保留完整版本 + 分段词项 |
| `attachments` | 同批上传的日志/截图 | 只存引用，不把二进制塞进索引 |

**小节归一化表**（只列常用，完整表在 `bbu/kb_ingest.py` 的 `SECTION_ALIASES`）：

| 原始标签 | 规范 kind |
|---|---|
| 详细描述、测试输入、预期结果、实际结果、测试环境、现象是否可以复现、发现日期、发生地点 | `symptom` / `environment` / `expected` / `actual` / `repro` / `meta` |
| 原因分析、原因描述、变更原因分析、变更影响分析 | `cause` |
| 处理方案、解决方案、修改建议、故障建议 | `solution` |
| 定位结果、定位时间、测试人员自定位信息、发生器件、以往版本是否存在 | `diagnosis` |
| 版本信息 | `version` |

### 2.4 多根因拆分规则

1. 以 `【原因分析】` 为块边界；同一文档内出现第 2 个及以后 `【原因分析】`，新建一条 `kb_cases`，标记 `is_derived=1`。
2. 每块内按 `【*1.定性】/【*2.是否其它变更引入】/【*3.原因描述】/【*处理方案】` 抽取子字段；缺失时留空，不阻断导入。
3. 第 1 条案例继承文档标题与现象；派生案例标题追加“（转交/派生）”，但保留同一 `doc_id`，便于引用原文。
4. 没有【原因分析】的记录（约 187 条）仍建 1 条案例，`cause` 为空、`quality` 降低，进入“待补充”队列，不阻塞检索。

### 2.5 质量分与状态机

质量分 0–100，按完整度计算：

- 有现象 25 分、有原因 25 分、有方案 25 分、有板卡/领域 10 分、有版本/复现/日期 10 分、来源可信度 5 分。
- 规则抽取置信度 0.9；LLM 辅助抽取 0.5–0.8；人工录入 1.0。
- `quality < 60` 或 `confidence < 0.7` 进入审核队列；`quality ≥ 80` 可直接发布（管理员可配置）。

状态机：

```text
draft → reviewing → active → disabled → archived
                 ↘ rejected
active ⇄ disabled（可恢复）
```

- `active` 才进入索引；`disabled` 保留数据但不参与检索；`archived` 只读、可恢复；删除为软删除，30 天后由清理任务物理删除。

## 3. 检索设计（召回率核心）

### 3.1 指标定义

| 指标 | 定义 | 目标 |
|---|---|---|
| Entity Recall@1 | 查询含板卡/告警/版本等精确实体时，目标案例是否第 1 条 | 100% |
| Symptom Recall@5 | 症状描述类查询，目标案例是否在前 5 条 | ≥ 99.5% |
| Open Recall@5 / @10 | 开放改写、口语、跨术语查询 | ≥ 97% / ≥ 99% |
| Overall Recall@5 | 300 条金标准总体（不含无答案集） | ≥ 99% |
| MRR@10 | 第一个相关结果名次的倒数均值 | ≥ 0.80 |
| Cause Coverage@5 | 宽泛查询下，前 5 条覆盖的根因类别比例 | ≥ 90% |
| No-answer Accuracy | 库内无相关案例时是否正确拒答 | ≥ 90% |
| Citation Validity | 回答中的每个 `[K#]` 是否对应真实检索结果 | 100% |
| P95 延迟 | 2268 案例、单机、单查询 | ≤ 50 ms |

### 3.2 预处理与分词

不使用 jieba，采用“规范化 + ASCII 词项 + 中文二元组 + 领域词”的混合方案：

1. **归一化**：NFKC、全角转半角、转小写、去零宽字符、统一 `：/－/（）`；保留 `0xfe`、`V4.30.20.00B219-1`、`slot6`、`核40` 等标识符。
2. **板卡规范化**：`VBPe2 / vbpe2 / VBPE2` → `VBPE2`；`VBPd6K / VBPD6K` → `VBPD6K`；`VSWd1 / VSWD1` → `VSWD1`。只统一大小写与别名，不合并不同型号。
3. **版本词项**：完整版本作为一个高权重词项；同时拆出 `v4`、`30`、`20`、`00b219` 等分段词项，兼顾“整版本精确匹配”和“只记得主版本”的查询。
4. **中文切分**：连续中文串生成重叠二元组（`基带板` → `基带`、`带板`），单词中文生成单字；这是无词典分词下对中文最稳的召回方式，代价是索引词项增多（实测 71,918 个词项、881,332 条倒排）。
5. **领域词**：板卡型号、告警名、故障词、部件名（EPLD、IPMB、SSD、SFP、1588、驻波、看门狗等）作为实体词单独入倒排，查询命中时额外加权。
6. **停用词**：只去掉“怎么/如何/什么/可以/需要/是否/以及/一个”等极少量疑问词；不用大停用词表，避免把“不复现”“未恢复”这类否定语义切掉。
7. **PII 脱敏**：姓名+工号、11 位手机号、邮箱、`工号：12345678` 在入索引前替换为 `〔人员〕/〔工号〕/〔电话〕/〔邮箱〕`；原文单独存 `raw_text`，仅管理员可读。
8. **SimHash**：对归一化词项做 64 位 SimHash，用于近重复检测与“相似案例”推荐；分 4 段建桶，汉明距离 ≤ 3 视为近重复候选。

### 3.3 索引结构

采用紧凑倒排，不用“每个文档五个 Counter”的高内存结构：

```text
terms:      term -> term_id
postings:   term_id -> array('I')        # 文档/案例号
tfs:        term_id -> array('H')        # 长度 = 5 × len(postings)，五字段 tf
field_len:  五条 array('I')              # 每条案例五个字段的长度
idf:        array('d')
```

五个字段及权重（来自原型调参，Phase 3 用金标准再做网格搜索）：

| 字段 | 内容 | 权重 \(w_f\) |
|---|---|---:|
| `title` | 清洗后的标题 + 原始标题 | 4.0 |
| `symptom` | 现象、实际结果、测试输入 | 2.2 |
| `cause` | 原因分析、原因描述 | 1.8 |
| `solution` | 处理方案、解决方案、修改建议 | 1.2 |
| `body` | 完整答案兜底 | 1.0 |

评分公式：

\[
\mathrm{score}(q,d)=\sum_{t\in q}\mathrm{IDF}(t)\cdot\sum_{f} w_f\,
\frac{tf_{t,f}(d)\,(k_1+1)}
{tf_{t,f}(d)+k_1\left(1-b+b\,\frac{|d_f|}{\overline{|d_f|}}\right)}
\]

取 \(k_1=1.2\)、\(b=0.75\)，\(\mathrm{IDF}(t)=\log\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right)\)。

辅助索引：

- **实体索引**：`(kind, value) -> array('I')`，kind 为 `board/domain/version/slot/alarm`。查询含实体时先取交集/并集，保证“板卡+故障词”不会因长文本稀释而漏召回。
- **短语索引**：标题与原因/方案的首句做归一化后存前缀哈希，支持“整句照抄”查询的精确命中。
- **SimHash 桶**：近重复与相似案例。
- **快照**：`data/kb/index/kb-<count>-<checksum>.bin`，JSON 头 + zlib 压缩的定长数组；加载失败自动回退重建。2268 条重建仅 1.5 秒，快照是优化项，不是正确性依赖。

**为什么不用 SQLite FTS5**：FTS5 的 `unicode61` 对中文按单字切分，召回与排序不可控；`trigram` 需要较新 SQLite 且对短词/标识符不友好。平台已有纯 Python BM25F 经验，自己实现可保证跨版本、跨平台一致，也符合零依赖约束。

### 3.4 查询理解

每次查询先产出 `QueryAnalysis`：

| 字段 | 识别方式 | 用途 |
|---|---|---|
| `terms` | 归一化 + 分词 | BM25F |
| `boards` | 正则 + 词典（VBPE2/VBPD6K/VSWD1…） | 实体通道、过滤、加权 |
| `domains` | 标题/正文标签词典（电源/时钟/存储/版本升级/复位/光/低速/高速/大容量） | 过滤、加权 |
| `versions` | `V\d+(\.\d+)+…`、`0xfe` | 精确加权 |
| `slots` | `slot\d+`、`\d+槽位` | 精确加权 |
| `intent` | 关键词：原因/为什么/怎么处理/如何解决/现象/复现/版本 | 字段权重动态调整 |
| `filters` | 前端显式筛选（板卡/领域/状态/时间） | 硬过滤 |
| `expansions` | 同义词/缩写/中英映射 | 查询扩展 |

意图对字段权重的影响：

- 问“原因/为什么/定位” → `cause` 权重 ×1.4；
- 问“怎么处理/解决/恢复/步骤” → `solution` 权重 ×1.4；
- 问“现象/表现/告警” → `symptom` 权重 ×1.3；
- 问“哪个版本/版本引入” → `version` 实体权重 ×1.5。

查询扩展规则：

- 只对“概念词”扩展，不对板卡型号、版本号、告警码扩展；
- 每个概念最多扩 2 个同义词，避免查询漂移；
- 同义词表可在管理页维护，内置种子见附录 B；
- 可选“深度检索”模式：用现有模型把口语问题改写为 3 条领域问法（只生成检索词，不生成答案），失败则退回原查询。

### 3.5 多路召回、融合与重排

| 通道 | 召回量 | RRF 权重 | 作用 |
|---|---:|---:|---|
| BM25F 词法 | top 50 | 1.0 | 主召回，覆盖自然语言描述 |
| 实体精确 | top 50 | 1.1 | 板卡/领域/版本/告警码命中，防长文本稀释 |
| 短语/整句 | top 20 | 0.9 | 复制粘贴整句、标题照抄 |
| 模糊/SimHash | top 10 | 0.6 | 近重复标题、错别字、少字 |
| 语义（可选） | top 50 | 0.8 | 仅当管理员配置了 embedding 端点；默认关闭 |

融合采用 RRF：

\[
\mathrm{RRF}(d)=\sum_{c}\frac{w_c}{k+\mathrm{rank}_c(d)},\quad k=60
\]

融合后取前 20 条做确定性重排，特征与初始权重：

| 特征 | 权重 | 说明 |
|---|---:|---|
| 归一化 BM25F | 0.50 | 词法相关性 |
| 实体覆盖 | 0.20 | 板卡/领域/版本命中比例 |
| 标题覆盖 | 0.10 | 查询词在标题中的覆盖率 |
| 小节命中 | 0.10 | 命中原因/方案/现象中的哪一类 |
| 来源质量 | 0.05 | quality/100 |
| 新鲜度 | 0.03 | 近 2 年案例轻微加权 |
| 完整度 | 0.02 | 有原因+方案优先 |

去重与多样性：

- 同一 `doc_id` 最多保留 2 条案例；
- 同一 `root_cause_key`（可得时）最多 1 条进前 5；
- 用 MMR（\(\lambda=0.72\)）在“相关性”和“与已选案例的差异”之间平衡，避免前 5 条都是同一根因的近似重复。

**槽位保证**：最终前 5 条至少包含“词法第 1”“实体第 1”“短语第 1”各一条（若存在），防止融合把某一路的强命中挤掉。这是“召回完美”工程实现的关键细节。

### 3.6 拒答与降级

- 归一化最高分 < `kb_no_answer_threshold`（初始 0.18）且无实体命中 → 返回 `no_answer=true`，展示“未找到足够相关的历史案例”，附带 3 条“可能相关”与放宽建议；不调用模型编答案。
- 有实体命中但案例质量分 < 50 → 返回“找到相似现象，但缺少原因/方案”，只展示原文小节，不生成结论。
- 模型不可用/超时 → 降级为“抽取式回答”：按模板列出前 3 条案例的标题、现象、原因、方案原文，明确标注“当前为本地检索结果，未经模型总结”。
- 过滤条件过窄导致 0 结果 → 明确提示“当前筛选条件下无结果”，并提供“清除板卡筛选/放宽领域”按钮。

### 3.7 原型实测基线

测试环境：当前云主机，纯标准库，单线程；语料为附件 2268 条 CSV，按文档级五字段索引。

| 测试集 | 样本数 | Recall@1 | Recall@3 | Recall@5 | Recall@10 | MRR@10 |
|---|---:|---:|---:|---:|---:|---:|
| 同题检索（sanity，标题原样） | 2268 | 98.94% | 99.96% | 100.00% | 100.00% | 0.9944 |
| 症状检索（去掉板卡/版本/标签） | 2254 | 94.41% | 98.62% | 99.29% | 99.91% | 0.9663 |
| 原因句检索（40–120 字原文句） | 400 | 87.75% | 94.25% | 95.75% | 97.25% | 0.9133 |

性能：

| 指标 | 实测 |
|---|---:|
| 索引构建 | 1.54 s（2268 条、181 万字） |
| 常驻内存增量 | 57.9 MB |
| 平均查询 | 11.7 ms |
| 词项数 / 倒排条目 | 71,918 / 881,332 |

同义词扩展的对照实验（无同义词 → 有同义词，P@5 为前 5 条中相关案例数）：

| 英文/术语查询 | 相关案例数 | 原始 P@5 | 扩展后 P@5 | 扩展后首个相关名次 |
|---|---:|---:|---:|---:|
| `watchdog reset baseband board` | 77 | 0 | 5 | 1 |
| `SFP optical module rx power low` | 9 | 0 | 4 | 1 |
| `fan speed abnormal` | 20 | 0 | 4 | 1 |
| `cell setup fail` | 36 | 0 | 2 | 1 |
| `board keeps rebooting link down alarm` | 7 | 0 | 1 | 5 |

结论：中文词法召回已经很强；**跨语言/缩写/现场叫法必须靠同义词层**，不能只靠字符二元组。同义词种子见附录 B。

> 说明：以上是“目标案例是否在 top-k”的工程基线，不是人工相关性评测。同题/症状/原因句都来自同一案例，能证明索引与分词有效，但不能替代 3.8 的专家金标准。原型以“文档”为索引单元；生产按“案例”拆分，案例文本更短、字段更纯，指标预计持平或略升，最终以 1.29.0 实测为准。

### 3.8 从“99%”到“接近完美”的六条措施

1. **金标准先行**：上线前构建 300 条查询、1–3 条相关案例/条的 `kb_eval` 数据集；按板卡 × 领域 × 难度分层，包含 40 条“库内无答案”的越界问题。每个版本跑一次，指标不达标不发布。
2. **候选池召回单独度量**：先测“前 100 条是否包含目标”（候选召回率），目标 99.9%；再测重排后的 R@5。这样能区分“没找到”和“找到了但排错”。
3. **实体精确保证**：查询同时含“板卡型号 + 告警/故障词”时，实体通道做交集，并强制进前 3；这类查询 R@1 必须 100%。样例里“VBPE2 看门狗复位”“EPLD 升级 0xfe”都属于此类。
4. **同义词与现场叫法持续沉淀**：管理页提供“词典”分区；零结果查询、点“无用”的查询进入 `kb_query_logs`，每周把高频未命中词补进同义词/别名表，并加入金标准。
5. **可选语义通道**：仅当现场配置了 embedding 能力的模型时开启；向量存 float32 数组，余弦用 `math.fsum` 计算；不引入 numpy。语义通道只做补充召回，不替代词法主链路。
6. **诚实的边界**：任何系统都不能保证任意改写 100% 命中。本计划承诺的是“库内已存在的目标案例，在实体精确查询 R@1=100%，症状描述 R@5≥99.5%，开放改写 R@5≥97%/R@10≥99%，总体 R@5≥99%，无答案可解释、可复盘”。发布说明里按这个口径写，不写“100% 永不漏”。

## 4. 导入与知识库管理

### 4.1 导入管线（8 步）

```text
选择文件/文件夹/粘贴文本/粘贴图片
  1 接收：multipart 流式落盘、SHA-256、大小/类型校验
  2 识别：扩展名 + magic bytes + 编码探测（UTF-8/GBK）
  3 解析：格式适配器 → 纯文本 + 结构提示
  4 抽取：模板规则优先，LLM 兜底 → 文档/案例/小节草稿
  5 去重：文件哈希 + 案例哈希 + SimHash 近重复
  6 审核：预览、编辑、置信度、警告；管理员批量通过
  7 入库：documents/cases/tags 事务写入
  8 索引：防抖 3 秒后台重建，原子切换；失败保留旧索引
```

关键实现：

- 上传落盘到 `data/kb/staging/<job_id>/`，完成审核后移动到 `data/kb/files/<sha256前2位>/<sha256>/<原文件名>`；
- 单文件默认上限 50 MB、单批 200 MB、单批 200 个文件；可配置；
- CSV 超过 5000 行时分批解析，每 500 行提交一次草稿，避免内存峰值；
- 后台最多 2 个解析线程；索引构建单独 1 个线程，避免和诊断任务抢 CPU；
- 每个文件独立事务，单个失败不影响整批；任务结束给出成功/失败/跳过统计与 CSV 报告。

### 4.2 格式适配器

| 格式 | 解析方式（纯标准库） | 输出 | 失败/降级 |
|---|---|---|---|
| CSV / TSV | `csv.Sniffer` + `csv.DictReader`；列名映射 `question/answer` 或用户指定 | 一行一文档，按模板拆案例 | 编码非 UTF-8 → 尝试 GBK；列不识别 → 进入列映射页 |
| TXT / MD | 直接读；MD 按标题层级切小节 | 文档/案例 | 超长按 2 MB 截断并警告 |
| DOCX | `zipfile` + `xml.etree`：`word/document.xml` 段落/表格，按 `w:pStyle` 识别标题 | 标题+正文+表格 | 加密/损坏 → 标记失败；嵌入图片可选视觉转写 |
| XLSX | `zipfile` + `sharedStrings.xml` + `worksheets/sheetN.xml`；处理 inlineStr、日期序列号 | 每行一条，首行作表头 | 多 sheet 逐个导入；公式取缓存值 |
| HTML | `html.parser` 去 script/style，保留标题/列表 | 标题+正文 | 富文本粘贴统一按纯文本转义 |
| PDF（文本型） | 自研 `kb_pdf.py`：解析对象/xref、`FlateDecode`、`Tj/TJ` 文本、ToUnicode CMap | 按页文本 | 扫描件/字体缺失 → 转视觉模型或人工 |
| PDF（扫描件） | 不内置 OCR；调用视觉模型按页转写，或进“待人工转写” | 结构化草稿 | 无视觉模型 → 保留 PDF 附件+人工录入 |
| 图片（PNG/JPG/WebP） | 只校验 magic bytes 与尺寸，不本地解码；调用视觉模型转写 | 草稿：标题/现象/原因/方案 | 无视觉模型 → 附件+人工录入表单 |
| 粘贴文本 | 直接进解析器；可选“按【】模板拆”或“整篇一条” | 草稿 | — |
| ZIP（可选） | `zipfile` 安全解压（防路径穿越/zip bomb），内部文件逐个走适配器 | 多文档 | 超限拒绝 |

**PDF 解析的边界要提前说清**：纯标准库无法可靠还原复杂排版/扫描件；v1 保证“文本型 PDF 可抽取”，扫描件走视觉模型或人工。管理页对每个文件显示 `parsed / needs_ocr / failed`，不假装成功。

**视觉转写的实现方式**：`bbu/ai.py` 新增 `complete_vision(role, prompt, image_bytes, mime)`，按 OpenAI 兼容格式发送 `image_url`（data URL），调用前检查模型能力（`model_capabilities` 或配置的 `kb_vision_model`）；模型不支持视觉或调用失败时，图片转“待人工转写”，不阻塞导入。视觉输出仍走 `KB_EXTRACT_SCHEMA`，并标记 `extraction_method=vision`、低置信度进审核。

### 4.3 结构化抽取

**规则优先**（覆盖 90% 的样例）：

1. 按 `【...】` 标签切小节，标签去序号/星号后映射到规范 kind；
2. `question` → 标题 + 现象；`answer` 前言 → 详细描述；
3. 原因块按 `【原因分析】` 切分；块内按 `【*3.原因描述】`、`【*处理方案】` 取字段；
4. 正则抽板卡型号、领域标签、版本、槽位、告警码；
5. 缺失字段留空并计质量分，不阻断。

**LLM 兜底**（仅非模板文本/图片转写）：

- 使用 `AIGateway.complete(role="assistant", json_schema=KB_EXTRACT_SCHEMA)`；
- Schema 固定：`title / symptom / environment / cause / solution / boards / domains / versions / confidence`；
- 提示词要求“只抽取原文存在的信息，不推断根因；找不到填 null”；
- 结果过与 `assistant_tools._validate` 同风格的手写校验，失败重试 1 次，再失败转人工；
- 所有 LLM 抽取结果标记 `extraction_method=llm`、`confidence`，默认进审核队列。

**不自动编造**：LLM 只做“把原文放进字段”，不允许补不存在的版本号、位号、处理步骤；抽取结果与原文做子串核对，关键字段（原因/方案）在原文找不到时降置信度并警告。

### 4.4 去重、版本与合并

- **文件级**：`source_sha256` 完全相同 → 直接跳过，提示“已导入过（文档 Kxxx）”。
- **案例级**：`hash(title_clean + symptom + cause + solution 归一化)` 完全相同 → 跳过或合并附件。
- **近重复**：SimHash 汉明距离 ≤ 3 → 标记“可能重复”，默认不自动合并；管理页展示候选原文，管理员选择“保留新的 / 合并附件 / 作为新版本”。
- **多文件合并为一条知识**：导入向导支持勾选多个文件“合并为一条故障”，例如一份分析报告 + 两张现场截图；合并后 `attachments_json` 记录全部文件，检索索引合并文本。
- **版本**：编辑/重新导入同标题同案例时，写 `kb_doc_versions` 快照，`version+1`；可回滚；索引只取当前 active 版本。
- **回收站**：软删除 30 天，可恢复；物理删除需二次确认并审计。

审计事件：`kb.import`、`kb.approve`、`kb.reject`、`kb.doc_update`、`kb.doc_disable`、`kb.doc_delete`、`kb.reindex`、`kb.term_update`、`kb.eval_run`、`kb.settings`。记录用户、文档/案例 ID、数量、IP、耗时；导出与删除额外记录。

## 5. 对话窗口与工具集成

### 5.1 问答链路

```text
用户问题 + 筛选
  → QueryAnalysis（实体/领域/版本/意图/扩展）
  → 多路召回（词法/实体/短语/模糊/可选语义）
  → RRF 融合 + 确定性重排 + MMR
  → 证据包（top 6，按字段裁剪，PII 脱敏）
  → AIGateway.complete(role=assistant, json_schema=KB_ANSWER_SCHEMA)
  → 引用校验 + 标识符核对
  → 结构化答案 + 案例卡片 + 检索详情
```

- 检索与回答解耦：`kb_service.search()` 可被工具、诊断、工坊复用；`kb_service.answer()` 只负责对话。
- 一次问答最多 6 条案例进上下文；每条按“标题 80 字 + 现象 300 字 + 原因 400 字 + 方案 400 字”裁剪，总预算 6000 字，避免小上下文模型超窗。
- 宽泛问题（如“看门狗复位有哪些原因”）额外取 top 50 做根因分布统计，回答中给出“案例分布”，不把 50 条全塞给模型。

### 5.2 答案结构与引用

`KB_ANSWER_SCHEMA`：

```json
{
  "answer": "结论性文字",
  "conclusions": [{"text": "...", "citations": ["K1"]}],
  "steps": [{"text": "...", "citations": ["K2"]}],
  "cautions": ["..."],
  "confidence": "high|medium|low",
  "no_answer": false
}
```

回答展示分四块：

1. **结论**：一句话说明“最可能的根因/处置方向”，标注置信度；
2. **匹配案例**：卡片列表，显示标题、板卡、领域、根因摘要、方案摘要、匹配理由（命中板卡/关键词/小节）、质量分；
3. **处理建议**：按步骤列出，每步带 `[K#]` 引用；冲突根因并列，不强行合并；
4. **参考与追问**：原文链接、复制、转诊断任务、继续追问。

引用规则：

- 每个结论/步骤至少 1 个 `[K#]`；`[K#]` 必须存在于本次检索结果；
- 回答中出现的版本号、板卡型号、告警码、数值，必须能在证据包中找到，否则标记“待核对”并降置信度；
- 不允许把模型自身经验写成“案例结论”；没有证据就写“知识库未收录”；
- 低置信度（top1 分数 < 0.35 或前两名差距 < 10%）时，答案首行提示“以下为相近案例，需结合现场日志确认”。

### 5.3 工具层接入（R1 的核心）

在 `bbu/assistant_tools.py::_register_all` 新增两个 `ToolSpec`：

| 工具 | 风险 | 作用 | 参数 |
|---|---|---|---|
| `search_fault_kb` | read | 检索历史故障案例，返回案例摘要、根因、方案、引用 | `query`（必填，≤300 字）、`board`（可选）、`domain`（可选）、`limit`（1–10，默认 5） |
| `get_fault_case` | read | 按案例 ID 取完整案例与小节 | `case_id`（必填）、`section`（可选） |

`search_fault_kb` 的返回同时带 `sources`：

```json
{"title": "VBPE2单板看门狗复位", "heading": "历史故障案例", "uri": "faultkb://case/K0001", "excerpt": "..."}
```

助手路由规则（写进 `bbu/assistant.py` 的规划提示）：

- “平台怎么用/怎么部署/怎么升级”→ `search_docs`；
- “某故障现象/原因/怎么处理/哪块板子”→ `search_fault_kb`；
- 两者都问 → 先 `search_fault_kb`，再 `search_docs`；
- 不允许用 `search_docs` 回答故障根因，避免平台文档与故障案例混淆。

MCP：

- 两个工具 `mcp="read"`，只读 Token 可用；写 Token 也不暴露导入/审核；
- 工具名、Schema 进入 `/api/mcp/info` 与 `tools/list`；
- 助手“工具执行卡片”显示“检索故障知识库：query / 命中 N 条”，来源卡片可跳 `#/kb/docs/{doc_id}`。

工具数量从 20 增至 22；同步更新 README、MCP 文档、`tests` 中的工具数量断言。

### 5.4 诊断与技能工坊联动

**诊断任务**：

- `planning` 阶段：用任务标题 + 描述 + 日志清单中的板卡/告警关键词检索 top 5，作为“历史相似案例（仅供参考）”注入规划提示；提示词明确“不得据此跳过日志证据”。
- `reporting` 阶段：`reports.py` 增加附录“历史相似故障参考”，列案例标题、根因、方案、链接；不进入 `claims` 校验，不影响根因仲裁。
- 任务详情页新增“历史相似故障”折叠面板；可一键“在知识库中查看”。
- 若最终根因与某历史案例根因一致，报告中标注“历史案例支持：K1”；不一致则不标注，避免误导。

**技能工坊**：

- 创建/分析阶段可检索相似案例，作为“参考案例”附在提示词后；
- 生成 skill 的 `cases` 仍以用户上传日志为准，历史案例不能替代正例/反例；
- 工坊页面提供“从知识库找相似案例”按钮，结果只读。

### 5.5 对话窗口 UI

`#/kb` 默认进入“问答”：

- 顶部：标题 + 板卡/领域/状态筛选 + “深度检索”开关 + “管理知识库”入口（管理员）；

### 5.6 查询日志与反馈

- `kb_query_logs` 记录：用户、查询、筛选、QueryAnalysis、top10 ID、耗时、是否零结果、模型、是否降级；

## 7. 非功能设计

### 7.1 性能与容量

| 场景 | 目标 |
|---|---|
| 2268 案例：构建 | ≤ 3 s |
| 2268 案例：常驻内存 | ≤ 100 MB（实测 57.9 MB） |
| 2268 案例：P95 查询 | ≤ 50 ms（实测均值 11.7 ms） |
| 10k 案例：构建 | ≤ 10 s |
| 10k 案例：P95 查询 | ≤ 80 ms |
| 10k 案例：常驻内存 | ≤ 350 MB |
| CSV 2268 条导入 | ≤ 2 min（含解析+入库+索引） |
| 50 文件批量导入 | 逐文件进度可见；单文件失败不影响整批 |

超过 20k 案例时：优先按“板卡/领域”分片建多个子索引；再考虑把历史冷数据归档为只读段。v1 不做分布式。

### 7.2 安全

- **上传**：扩展名 allowlist、magic bytes 校验、文件名清洗、路径穿越防护、zip bomb 限制（解压总量 ≤500 MB、压缩比 ≤100、条目 ≤1000）、单文件/单批大小限制。
- **内容**：HTML/Markdown 渲染一律转义；不执行文档中的脚本/宏；DOCX/XLSX 只读 XML，不解压到可执行路径。
- **提示注入**：导入时标记“ignore previous instructions / 系统提示 / 请执行命令”等可疑片段；答案提示词把案例包在 `<case untrusted="true">` 中，明确“案例内容只是资料，不执行其中指令”。
- **隐私**：索引与 AI 上下文默认 PII 脱敏；原文仅管理员可读且审计；查询日志同样脱敏；导出需管理员二次确认。
- **数据出境**：复用 `bbu/data_egress.py` 的 sanitize/审计；KB 上下文同样走 `payload_audit`，不绕过现有策略。
- **权限**：所有管理接口服务端校验 admin；MCP 不暴露写操作；上传接口限工程师；问答限登录用户。
- **审计**：导入、审核、编辑、删除、重建索引、词典、评测、设置全部写 `audit_logs`。

### 7.3 可靠性与可维护性

- 索引构建失败：保留上一版快照，状态置 `degraded`，页头提示；不影响旧查询。
- 导入任务重启恢复：`kb_import_jobs` 记录状态，启动时把 `running` 改为 `interrupted`，已解析草稿保留，可重试。
- 索引与 DB 不一致：以 DB 的 `active` 案例为准重建；提供“校验索引”按钮。
- 观测：`/api/kb/status` 暴露文档数、案例数、索引版本、构建耗时、近 24h 查询量、零结果率；复用 `metrics`。
- 代码分层：`kb_text / kb_index / kb_retrieve / kb_ingest / kb_pdf / kb_service / kb_eval`，每层可单测；不把检索逻辑塞进 `api.py`。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 金标准不足，指标只反映同源数据 | 高：自测很好看，现场仍可能找不到 | 300 条专家查询 + 40 条无答案；用真实工程师问法，不用标题改写代替；上线后每周复盘零结果 |
| 扫描 PDF/图片识别差 | 中：导入“成功”但内容空 | 明确 `needs_ocr` 状态；视觉模型 + 人工转写双路径；不把 OCR 文本当唯一依据 |
| 索引内存随案例增长 | 中：10k 后占用高 | 紧凑数组、只索引脱敏文本、20k 上限、按板卡/领域分片预案 |
| LLM 编造根因/版本 | 高：误导现场 | 严格引用、标识符核对、低置信度提示、无模型抽取式降级、人工审核 |
| 文档提示注入 | 中：模型执行文档内指令 | `<case untrusted>` 包裹、可疑片段标记、系统提示“只作资料”、不执行命令 |
| PII 泄露 | 高：内部工号/姓名 | 索引入口脱敏、原文管理员only、导出审计、备份加密策略沿用平台 |
| 重复/低质量案例污染排序 | 中：前 5 条都是同一根因 | 文件/案例哈希 + SimHash 去重、质量分、MMR、同根因上限 |
| 升级迁移失败 | 高：现场不可用 | schema 只新增、幂等；`kb_enabled` 开关；升级/回滚演练；旧索引可重建 |
| 范围膨胀（多库/图谱/向量） | 中：延期 | 本期明确单库、纯词法；语义/多库列入后续版本 |

## 11. 已定的默认决策

以下按“自主规划”先定默认值，实施中可调整：

1. **单知识库**：默认 `BBU故障案例库`，`kb_id=1` 预留；不建多库切换。
2. **案例级检索**：文档可含多案例；前 5 条按根因去重，避免同名重复。
3. **工程师上传进审核**：管理员可配置直接生效；避免低质量资料污染共享库。
4. **PII 默认脱敏**：索引、回答、日志都脱敏；管理员可看原文，留审计。
5. **图片默认“视觉模型优先，人工兜底”**：不内置 OCR 引擎，不增加包体。
6. **无模型时降级为抽取式回答**：仍可用，不阻塞现场。
7. **发布只发标准离线包**：不额外发 Windows 包/测试包，除非明确要求。

## 附录 A：原型方法与结果

- 语料：附件 `故障知识库示例.csv`，2268 条，UTF-8 BOM；按 `question/answer` 读取。
- 索引：文档级五字段；ASCII 词项 + 中文重叠二元组；BM25F（\(k_1=1.2, b=0.75\)，字段权重 4.0/2.2/1.8/1.2/1.0）；紧凑 `array('I')` 倒排 + 五字段 `array('H')` tf。
- 评测：同题检索用原 `question`；症状检索去掉开头 `(...)`、`[...]`、板卡型号、版本号；原因句检索从【原因描述】随机抽 40–120 字句子；均以原案例为目标。
- 硬件：当前云主机，单线程，Python 标准库；数据为单次运行结果，未做多轮取均值。
- 结果：见 3.7；同义词对照见 3.7 第二张表。
- 代码：原型脚本保留在开发工作区，P1 会整理为 `bbu/kb_index.py` 骨架与 `tools/bench_kb.py`，不直接复用临时脚本。
