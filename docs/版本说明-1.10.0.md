# 版本说明 1.10.0

> 后续补丁：1.10.1 修复浏览器 favicon 旧缓存、Ubuntu 16.04 备份脚本解释器选择和缺失静态资源误回退问题，详见 `docs/版本说明-1.10.1.md`。

基线：1.9.0（schema 9）→ 1.10.0（schema 10）
日期：2026-11-25

## 一、本版内容

本版把上一轮优化计划落到源码、数据库和页面，重点解决术语不一致、配置不透明、用户字段冗余、任务详情过载、工坊交互过重、磁盘空间不可见和运维入口分散。数据库升级为 schema 10，旧库采用加法式 `ALTER`，不重建表。

### 1. 术语统一：用户可见“病例”全部改为“案例”

- 源码、页面、工具、测试和文档中约 205 处用户可见“病例”已改为“案例”，覆盖 31 个源文件及一处 CSS 注释。
- 保留 `real_cases`、`cases`、`cases_dir` 等数据库表名和 API 字段，不做破坏性改名。
- “现场真实案例库”（`real_cases`）与“技能回归案例”（`cases/cases_dir`）仍是两个对象，只统一用户措辞，不合并数据模型。

### 2. 数据库 schema 10

新增字段和表：

- `users.domain`：用户领域，列表、搜索、详情和审计均支持筛选。
- `tasks.title_source`：`manual/deterministic/ai`，记录标题来源。
- `workshop_drafts.name_auto`、`name_locked`：自动命名开关与锁定状态；历史草稿迁移默认关闭自动命名。
- `workshop_jobs`：工坊后台任务，含状态、阶段、进度、消息、参数、结果、错误和时间戳。
- `storage_jobs`：任务空间释放任务，含状态、阶段、进度、释放字节、摘要和中断恢复信息。
- `bbu/migration.py` 导出的 manifest `schema_version` 同步改为 10；迁移、升级和用户管理测试断言同步更新。

### 3. 模型配置默认公司 MaaS，支持不保存测试

- 新建模型默认填入公司 MaaS：`https://nebulacoder-maas.zte.com.cn/v1`、默认模型 `deepseek-v4-flash`、名称“公司 MaaS”。
- 模型名输入框提供公司模型 datalist：`deepseek-v4-flash`、`nebulacoder-lite-v7.0`、`nebulacoder-lite-cot-v7.0`。
- 新增 `POST /api/models/test`（`h_model_test_draft`）：直接测试当前表单填写值，不落库、不写模型记录；旧 `POST /api/models/<id>/test` 保留。
- 编辑模型时 API Key 留空表示复用已保存密钥；未填 Key 测试非 Mock 模型会明确提示“请填写 API Key（mock 除外）”。
- 模型不可用、未配置或调用失败时，任务详情和工坊页面直接显示提示，并继续确定性路径，不伪装 AI 已生效。

### 4. 新建诊断取消人工标题，AI 自动命名

- 新建诊断页去掉标题输入，只保留故障描述、日志包、诊断模式和灰度选项。
- 创建时先用描述首行生成确定性占位标题并写 `title_source=deterministic`；旧客户端带标题仍接受，记 `manual`。
- 规划提示词要求同时返回 40 字内中文故障标题；流水线在计划写入后调用 `_apply_task_title`，过滤空泛标题，更新任务表并记录标题来源事件。
- AI 失败、标题为空或非法时保留确定性标题，任务照常执行；列表和详情显示最终标题。

### 5. 任务详情改为四个一级分区

- 一级分区固定为：**诊断概览、证据与技能、诊断报告、运行详情**。
- 运行中首次进入默认“诊断概览”；已完成且有报告首次进入默认“诊断报告”。
- SSE 刷新保留当前分区、滚动位置和报告视图，不强制跳回默认页。
- 报告 iframe 按需加载，切到“诊断报告”才请求；原阶段时间线和执行时间线移入“运行详情”。

### 6. 用户管理只保留必要字段

- 创建用户表单只有四项：用户名（同时作为默认显示名）、角色、领域、初始密码。
- 管理员创建账号的初始密码可为 9 位，默认 `bbu-skill`；首次登录仍强制改密。普通用户自主改密至少 10 位。
- 邀请开户、班组、站点、独立显示名入口隐藏；旧邀请 API 保留兼容。
- 新增 `domain` 字段，用户列表、详情、搜索、审计均支持按领域过滤。

### 7. 技能工坊：引导式流程、后台任务与真实进度

- 工坊页面改为“资料输入 → AI 解析与命名 → 规则审查 → 案例回归 → 构建发布”五步引导；高级 Profile YAML 默认折叠。
- 新增 `WorkshopJobService`，接入 `App.__init__`、`run.py` 关闭流程和 API；创建、日志上传、分析、补充重建、构建、案例写入均支持 `?async=1`，返回 202 `{job}`。
- 任务阶段：`queued -> starting -> unpack -> extract -> review -> repair -> review-final -> check -> done`；失败/中断写 `last_error` 并改草稿状态，前端显示重试入口。
- 前端改为异步任务轮询，显示真实阶段和百分比，不再只显示“处理中”；模型下拉可选择覆盖模型，失败时显示明确提示与“配置个人 Key”入口。
- 案例列表显示自动递增的 `case-01` 下一 ID、正例/反例、期望根因、命中规则和上传文件；正例根因必填，反例固定 `NONE`，重复案例需勾选覆盖。
- 自动命名：首次创建草稿生成简洁占位名称，AI 可用时补充 40 字内中文标题；首次构建或写入案例后锁定名称。修复了自动名称超过 64 字符导致 profile 校验失败、标签解析把整段资料塞进故障名、案例上传丢失扩展名、覆盖案例产生重复归档名导致回归无法解包、成功构建后旧错误不清理等问题。

### 8. 任务空间统计与选择性释放

- 新增 `bbu/task_storage.py`：统计每任务原始输入、任务中间产物、合计、共享引用、可立即释放字节和磁盘剩余。
- 新增接口：`GET /api/storage/overview`、`POST /api/tasks/<id>/release`（202 `{job}`）、`GET /api/tasks/<id>/storage-jobs`、`GET /api/storage/jobs/<job_id>`。
- 后台 `storage_jobs` 按 `releasing -> released` 执行，只删除 `data/uploads` 下原始文件，保留报告、证据、案例和数据库记录。
- 重跑任务共享同一批输入；释放前扫描所有任务引用，已释放/迁移排除任务不再算引用者，只有最后一个引用者释放时才真正删除共享文件。
- 服务重启时 `releasing` 自动恢复为 `release_interrupted`，可重新发起；运行中任务拒绝释放。
- 系统页新增表格：勾选任务、二次确认、轮询真实进度、完成/失败/释放字节汇总，并在完成后自动刷新统计。

### 9. 运行时配置在线编辑与网页重启

- `Config.RUNTIME_SETTINGS` 白名单、`runtime_items()`、原子 `save_runtime()`：保存前备份 `config.json.bak`，临时文件写完后 `os.replace`；环境变量覆盖字段页面禁用且保存被拒绝。
- 系统页新增“并发、预算与容量参数”编辑器，覆盖任务/工坊/空间释放并发与队列、LLM 调用/Token/超时/重试/健康窗口、补规划、规划范围、上传/解压/迁移容量。
- 新增 `GET/PUT /api/system/runtime-config`（仅管理员）和 `POST /api/system/restart`（仅管理员，202；有运行任务返回 409 `detail.blockers`）。
- 网页重启不重启进程：`App.request_restart()` 设置事件并定时 `server.shutdown()`；`run.py` 在 `serve_forever()` 返回后调用 `shutdown_services()`、关闭旧 server，再重新 `Config()` + `App()` + `AppServer()` 装配，监听同一端口。
- 页面重启期间显示遮罩和进度，自动轮询 `/api/health` 恢复；成功后自动刷新页面。

### 10. 统一运维脚本

新增 `tools/bbu_ops.py` 及 `tools/bbu-ops`、`tools/bbu-ops.cmd`：

```text
status   doctor   start   stop   restart   logs   backup   storage   release   config
```

- 支持 systemd 与手动 PID 两种模式；手动模式日志写 `data/logs/ops-run.log`。
- `storage` 调用空间统计/释放；`doctor` 检查运行环境、配置、目录、数据库和端口。
- 离线 `release` 只在服务未运行且明确加 `--yes` 时允许，避免误删线上输入。
- 已实跑 `status`、`doctor`、`storage`；`backup`、systemd `start/stop/restart` 和离线 `release` 仍需目标机验收。

## 二、升级说明

- 升级包：`dist/bbu-fault-platform-1.10.0-offline.tar.gz`（只含代码，不含 Python 运行时）
- 一键部署大包：`dist/bbu-fault-platform-1.10.0-ubuntu1604-offline.tar.gz`（含 CPython 3.13 运行时）
- Windows 手动包：`dist/bbu-fault-platform-1.10.0-windows.zip`
- 数据库：schema 9 → 10，加法式迁移；`workshop_jobs/storage_jobs` 自动建表，旧任务 `title_source` 为空时按旧标题处理。
- 已做 1.8.0（schema 8）→ 1.10.0（schema 10）离线升级演练：`upgrade_offline.sh --no-service` 自动生成 state/code 备份、保留原 admin 记录、完成幂等迁移并启动健康检查返回 1.10.0。
- Linux 升级：优先使用平台「系统信息 → 离线升级」上传 tar.gz，由 root 助手执行；也可用 `deploy/upgrade_offline.sh`。
- Windows 升级：停止平台，备份 `data/` 和 `config.json`，覆盖程序目录后重启。
- 迁移包与离线升级包不是同一种文件：`.bbumig` 只用于实例迁移/灾备恢复，不能用于升级或回滚。

## 四、已知限制

- 当前构建环境没有真实 Windows 主机和 root/systemd，Windows 重启激活、Linux 助手真实停服/重启、sudoers 和健康检查仍需目标机验收。
- `tools/bbu_ops.py` 的 `backup`、systemd `start/stop/restart` 和离线 `release` 未在真实 systemd 环境实测；手动模式 `status/doctor/storage` 已实跑。
- 浏览器验收使用临时实例（`127.0.0.1:8099`、数据 `/tmp/bbu-ui-check`），未接入真实公司 MaaS；工坊 AI 命名和成功测试路径由确定性解析与假模型覆盖，真实 MaaS 的延迟、限流和错误码需现场验证。
- 网页重启在同一 Python 进程内重装配 `AppServer`，进程级 uptime 不会归零；页面显示的是进程运行时长，不是单次服务启动时长。
- 任务空间释放只覆盖 `data/uploads` 原始输入；工坊日志/解压目录和任务中间产物当前保留，后续如需进一步回收可扩展 `storage_jobs` 范围。
