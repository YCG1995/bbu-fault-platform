# BBU 故障知识库优化计划（1.31.0）

> 审查对象：《BBU故障知识库优化改造计划-2026-11-27.md》  
> 审查基线：当前 `1.30.5`，提交 `6ea7f0a`，schema `25`  
> 目标版本：`1.31.0`（合并交付，不拆 1.30.6）  
> 本轮结论：原计划 R1、R2、R3、R6 仍然成立；R4 需并入多库统计；R5、R7、R8 不作为本轮前置；新增的导航拆分、多知识库、导入生命周期、审核批量和执行轨迹统一纳入 1.31.0。

## 1. 结论摘要

### 1.1 对你上传文档的审查结论

原计划以 1.30.1 为基线、把 R1–R3 排在 1.30.2 热修，但当前已经到 1.30.5，这三项并没有真正关闭：

| 原计划项 | 当前实现核对 | 判定 | 本轮处理 |
|---|---|---|---|
| R1 状态与文档编辑事务 | `_replace_document` 仍硬编码 `status='active'`、`deleted_at=NULL`；`_document_payload` 只读 active 案例，编辑停用文档会重新激活并可能软删除停用案例 | **仍成立，必须做** | 并入 P0，作为多库改造前的数据一致性底座 |
| R2 审核规则引擎 | `_normalize` 仍采信模型自报的 `decision` 与 `score`；模型返回 pass 时 blocker/低安全分不会强制 reject | **仍成立，必须做** | 并入 P0；同时重做审核区，避免批量操作放大错误 |
| R3 修订链统一写入口 | `decide_review` 仍直接 `UPDATE kb_cases SET status=...`，不写修订链 | **仍成立，必须做** | 并入 P0；审核通过/驳回/采纳 patch 全部走统一状态入口 |
| R4 统计口径 | `status`/`kb_stats` 的 `active_cases` 只统计案例自身 active，没有联表判断所属文档 active/deleted | **成立，需修正** | 并入多库统计；每个库单独口径 |
| R5 检索性能 | 本轮没有实测新基线；多库会增加索引数量，但单库检索逻辑不变 | **可做，但不是本轮前置** | 先记录基线；跨库检索后再看是否回归，不在本轮做大规模重排优化 |
| R6 管理输入闭环 | `_process_job` 仍把导入文件的 `doc_id` 写成空串，没有 `doc_ids_json`/`draft_ids_json`，批次回退没有可靠依据 | **部分成立，必须做关联部分** | 做逐文件 doc/draft 关联、逐文件结果、旧任务标记；文本/图片粘贴本轮不做 |
| R7 安全与资源加固 | ZIP/PDF/XML 解压膨胀、批大小依赖元数据等风险仍在 | **可做，但独立于本轮目标** | 推迟到后续版本（建议 1.31.1）；本轮只做备份导入的 zip 路径/大小校验 |
| R8 评测与术语 | `eval` 仍有硬编码示例数字，`terms` 仍是只读占位；300 条金标准未就绪 | **不能作为本轮发布门禁** | 本轮只清理误导文案；真实评测、300 条金标准、术语编辑推迟 |

原计划没有覆盖你本轮提出的这些现场问题：导航拆分、名称替代 ID、导入去重与批量回退、审核区标签化与批量、AI 审核模型、知识库执行轨迹、多知识库及备份迁移删除。这些需要单独补进计划，不能只按原文档的 R1–R8 推进。

### 1.2 本轮已确认的产品决策

1. **导航**：左侧导航拆成「故障问答」和「知识库管理」两个入口，都放在“诊断”组；去掉页面内重复的双主标签；知识库管理仅管理员可见。
2. **多知识库**：逻辑独立库，专家库/语料库同构；问答支持勾选多个库做跨库检索，管理和备份按库独立。
3. **重复与回退**：同一文件按 SHA-256 跨任务、跨草稿查重，重复默认跳过；批次回退把本批新增文档停用、草稿退回，保留版本和修订链，可恢复。
4. **交付**：所有改动合并为 `1.31.0`，一个标准 Linux 离线包。

### 1.3 本轮明确不做

- 不引入向量库、embedding 服务、OCR 引擎、前端框架或新的第三方运行时依赖。
- 不做图片/扫描件视觉转写，不做 300 条专家金标准正式验收，不做完整 R5 性能重写和 R7 安全加固。
- 不默认开启 AI 自动发布；批量审核仍然是人工显式操作。
- 不把现有单库拆成多个 SQLite 文件；采用同一数据库内的逻辑库命名空间，保证单机部署、单包升级和跨库检索。
- 不做知识库的物理硬删除 UI；删除默认是归档/软删除，物理清理走离线维护流程，避免破坏 append-only 修订链。

## 4. 多知识库架构

### 4.1 总体模型：同一数据库内的逻辑独立库

不拆多个 SQLite 文件，原因：

- 现有单机离线部署、备份、迁移、测试都围绕一个 `data/bbu.db`；
- 跨库检索需要在同一进程内合并多个索引，分库文件会显著增加连接和事务复杂度；
- 逻辑库已经能实现“文档/案例/索引/审核/备份独立”，满足专家库、语料库的管理诉求。

库的隔离边界：

- 文档、案例、导入任务、草稿、审核、查询日志、统计、索引、源文件都带 `kb_id`；
- 每个库独立索引、独立备份包、独立删除/归档；
- 用户可在问答页选择一个或多个库；管理页一次只操作一个库。

### 4.2 数据模型（schema 25 → 26）

新增表：

```sql
CREATE TABLE kb_libraries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  slug TEXT NOT NULL UNIQUE,
  kind TEXT NOT NULL DEFAULT 'fault',      -- fault / expert / corpus
  description TEXT NOT NULL DEFAULT '',
  visibility TEXT NOT NULL DEFAULT 'all',  -- all / reviewer / admin
  status TEXT NOT NULL DEFAULT 'active',   -- active / archived / deleted
  is_default INTEGER NOT NULL DEFAULT 0,
  created_by INTEGER,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT
);
CREATE UNIQUE INDEX idx_kb_libraries_one_default
  ON kb_libraries(is_default) WHERE is_default=1 AND status='active';
```

新增/扩展列：

```sql
-- 已有 kb_documents.kb_id，但插入时硬编码为 1，需要改为按当前库写入
ALTER TABLE kb_cases ADD COLUMN kb_id INTEGER NOT NULL DEFAULT 1;
ALTER TABLE kb_import_jobs ADD COLUMN kb_id INTEGER NOT NULL DEFAULT 1;
ALTER TABLE kb_drafts ADD COLUMN kb_id INTEGER NOT NULL DEFAULT 1;
ALTER TABLE kb_reviews ADD COLUMN kb_id INTEGER NOT NULL DEFAULT 1;
ALTER TABLE kb_query_logs ADD COLUMN kb_id INTEGER NOT NULL DEFAULT 1;
ALTER TABLE kb_query_logs ADD COLUMN kb_ids_json TEXT NOT NULL DEFAULT '[]';

-- 导入批次与文档/草稿的可靠关联，回退的基础
ALTER TABLE kb_import_files ADD COLUMN doc_ids_json TEXT NOT NULL DEFAULT '[]';
ALTER TABLE kb_import_files ADD COLUMN draft_ids_json TEXT NOT NULL DEFAULT '[]';

-- 去重与内容版本
ALTER TABLE kb_documents ADD COLUMN content_sha256 TEXT NOT NULL DEFAULT '';
ALTER TABLE kb_drafts ADD COLUMN source_sha256 TEXT NOT NULL DEFAULT '';
ALTER TABLE kb_drafts ADD COLUMN content_sha256 TEXT NOT NULL DEFAULT '';

-- 审核模型原始结论，保留可审计性
ALTER TABLE kb_reviews ADD COLUMN model_decision TEXT NOT NULL DEFAULT '';

```

索引元数据改为按库：

```sql
CREATE TABLE kb_library_index_meta (
  kb_id INTEGER PRIMARY KEY,
  version INTEGER NOT NULL DEFAULT 0,
  doc_count INTEGER NOT NULL DEFAULT 0,
  case_count INTEGER NOT NULL DEFAULT 0,
  terms INTEGER NOT NULL DEFAULT 0,
  bytes INTEGER NOT NULL DEFAULT 0,
  build_ms INTEGER NOT NULL DEFAULT 0,
  built_at TEXT NOT NULL DEFAULT '',
  checksum TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'empty',
  error TEXT NOT NULL DEFAULT ''
);
```

旧的 `kb_index_meta(id=1)` 保留一个版本用于回滚兼容；新代码优先读 `kb_library_index_meta`，没有时对库 1 回退读旧表。

统计日快照：`kb_stats_daily.dim_key` 写入 `kb:{id}`，不新增表；旧的空 `dim_key` 视为全库聚合。词典 `kb_terms` 增加 `kb_id INTEGER NOT NULL DEFAULT 1`，先支持库级词典，默认库 1。

### 4.3 索引与检索

`KBService` 从单索引改为索引映射：

```text
_indexes: dict[kb_id, KBIndex]
_dirty: set[kb_id]
_rebuild_queue: queue[(kb_id, generation)]
```

- `ensure_index(kb_id)`：按库懒加载；单库未构建时才构建。
- `rebuild_index(kb_id=None)`：指定库重建；全量重建只用于迁移/维护。
- `_build_index_locked(kb_id)`：SQL 增加 `AND d.kb_id=?` 与 `AND c.kb_id=?`；仍然使用 `case.status='active' AND doc.status='active' AND doc.deleted_at IS NULL`。
- `status`、`facets`、`list_documents`、`stats`、`list_jobs`、`list_drafts`、`list_reviews`、`list_operations` 全部增加 `kb_id` 过滤；不带参数默认库 1。
- 文件路径：库 1 继续兼容 `data/kb/files/<sha>`；新库使用 `data/kb/files/<kb_id>/<sha>`。解析时先查库目录，库 1 再回退旧路径。

跨库检索：

1. 用户选择 `kb_ids=[1,2]`。
2. 对每个可访问库分别 `retrieve(index, query, filters, limit=top_k*2)`。
3. 按 `1/(60+rank)` 做 RRF 合并；同一 `case_id` 只保留一次；保留每库最高名次，避免大库淹没小库。
4. 合并后取 `top_k`，每条结果附加 `kb_id`、`kb_name`、`library_kind`；引用仍编号 `K1..K6`，来源里带库名。
5. 单库选择时**完全走原有单库 `retrieve` 路径**，不引入 RRF，保证 1.30.5 的排序不回归。

查询日志：

- `kb_query_logs.kb_id` 记录主库（单库时就是该库；跨库时取第一个选中库）。
- `kb_ids_json` 记录实际检索库集合，统计按集合去重，避免跨库查询被重复计数。

### 4.4 权限

- 库管理（创建/重命名/归档/删除/备份/恢复）仅管理员。
- 问答可见性：
  - `all`：所有登录用户可检索；
  - `reviewer`：专家及以上可检索；
  - `admin`：仅管理员可检索。
- 管理页的库切换只显示当前用户可管理的库；第一版管理权限仍统一为管理员，暂不做库级管理员。
- 专家库默认建议 `reviewer`，语料库默认 `all`；创建时可在对话框中调整。默认故障知识库为 `all`。

### 4.5 备份、迁移、删除

备份格式：`*.kbbackup.zip`

```text
manifest.json          # 格式版本、schema、库元信息、计数、校验和、ID 映射
documents.jsonl        # 文档元数据、raw/masked 文本、hash
cases.jsonl            # 案例字段、标签、审核状态、来源 doc
drafts.jsonl           # 草稿 payload、状态、来源 job
reviews.jsonl          # 审核记录、模型原始结论
revisions.jsonl        # 案例修订链、哈希链字段
terms.jsonl            # 库级词典（可选）
files/                 # 可选：原始附件/导入文件，按 sha 命名
```

规则：

- 导出不包含内存索引；导入后重建索引。
- 导入默认创建新库，重新分配 doc/case/draft ID，manifest 保留 `source_id` 映射；避免跨实例 ID 碰撞。
- 导入到已有库时按 `content_sha256`/`source_sha256` 去重，重复跳过并计数；这是“迁移合并”模式。
- 备份导入必须校验：zip 路径穿越、单文件/总解压大小、manifest schema、计数、校验和；不合格直接拒绝。
- 删除库默认 `archive`：立即从问答/管理列表隐藏，数据保留，可恢复。
- 物理删除只提供离线维护脚本：需先导出备份、停止服务、二次确认库名；修订链是 append-only，物理清理不删除 `kb_case_revisions`，保留审计，只清理文档/案例/草稿/审核/源文件。这样既满足“删除库”，又不破坏审计链。
- 默认库不能删除；必须先指定另一个默认库。

“迁移”在第一版就是：源实例导出备份 → 目标实例“从备份导入为新库/合并到现有库”。不做实例间直连传输。

### WP1 状态、审核规则与修订链（P0，3 人日）

对应原计划 R1/R2/R3。

**状态与文档编辑**

- `_document_payload` 增加 `include_inactive`；管理员详情读取全部未删除案例，不再只读 active。
- `_replace_document` 增加 `preserve_status=True`、`delete_missing=False`；删除 `status='active'`、`deleted_at=NULL` 的硬编码。

- 文档详情页增加“显示停用案例”开关；停用案例显示“启用”按钮。

**审核规则**

- 新增 `bbu/kb_review_rules.py`，纯标准库：
  - `normalize_review(parsed, target_type)`：维度缺失/分数不可解析→`needs_review`；`score` 重算为六维之和；模型原始 `decision/score` 存入 `model_decision/model_score`。
  - `decide_review(dimensions, issues, score, confidence)`：任一 blocker、安全隐私 <5、来源忠实 <4 → `reject`；六维 ≥85 且无 blocker → `pass`；其余 `needs_review`；confidence <0.6 时 pass 降级。
  - `validate_patch(patch)`：只允许案例字段，拒绝命令、URL、脚本、超长值。
- `ReviewService._normalize` 改为调用规则；最终 `decision` 不再直接采信模型。
- `decide_review` 人工通过前再次校验 blocker；有 blocker 时拒绝 approve，提示先采纳 patch 或驳回。
- `review-v1` → `review-v2`，旧缓存不命中；新 prompt 版本写入 `kb_reviews.prompt_version`。

**修订链**

- `decide_review` 不再直接 `UPDATE kb_cases SET status`；通过/驳回调用统一 `apply_case_status`，写 `review_approve`/`review_reject` 修订。
- 文档分支调用 `apply_document_status`，写审计事件；不隐式改案例。
- 所有状态迁移必须带 `reason`；`verify` 在通过/驳回/patch 三条路径均返回 `ok=true`。
- 保留 `db.audit` 作为独立审计，但案例内容/状态以修订链为准。

**验收**

- 停用文档改标题/正文后仍 disabled；停用案例改标题后仍 disabled，不被标 deleted。
- 模型 `pass` + blocker → 最终 `reject`；`safety_privacy=0` 或 `source_fidelity=0` → `reject`；score 与六维和一致。
- 人工对 blocker 点通过 → 409/400；修订链 verify 通过。
- `pytest` 新增用例全绿。

### WP2 导入生命周期与批量管理（P0，4 人日）

对应你的 2b。

**可靠关联**

- `_insert_document` 返回 `doc_id`；`_create_draft` 返回 `draft_id`；`_process_job` 收集本文件产生的全部 ID，写回 `kb_import_files.doc_ids_json`/`draft_ids_json`，并保留单值 `doc_id` 兼容旧数据。
- `get_job` 返回 `doc_ids`、`draft_ids`、`doc_links`、`draft_links`；每个文件行显示文档/草稿名称。
- 旧任务（1.30.5 及以前）没有可靠关联，迁移时标记 `rollback_supported=false`；UI 禁用回退并提示“旧任务只能删除记录”。

**去重**

- 文件级：`kb_import_files.sha256` 精确查重，范围包括所有任务（不限当前任务）和所有状态为 `done/skipped` 的文件；命中则 `status='skipped'`，`error='重复文件，已跳过'`，`stats.skipped += 1`。
- 文档级：新增 `kb_documents.content_sha256 = sha256(规范化 raw_text)`；导入前查 `kb_documents`（未删除，含 disabled）和 `kb_drafts`（reviewing/approved）的内容 hash，命中跳过。若命中的文档已 `disabled`，跳过原因显示“已存在但已停用，请在文档库恢复”，并给出文档链接；管理员可显式勾选“强制导入”绕过。
- 草稿级：`kb_drafts` 增加 `source_sha256`/`content_sha256`；审核中的草稿也参与查重，解决“review 模式重复导入生成多个草稿”的根因。
- 同一批次内用内存 Set 去重，避免并发/顺序重复。
- 审批兜底：`approve_draft` 入库前再按内容 hash 查一次；若已有同内容文档，草稿标记 `duplicate`，返回已有 `doc_id`，不重复插入。批量批准同样逐项走这个兜底。
- 管理员可对单次导入勾选“强制导入”绕过查重；默认不勾选，用于确实需要保留同内容不同来源的场景。

**批量操作**

- `POST /api/kb/import/jobs/batch`：
  - `action=rollback`：把本批新增文档设为 `disabled`、草稿设为 `rejected`（原因“批次回退”），保留版本和修订链；不动人工后来新增的文档。
  - `action=delete`：只删除导入任务记录、文件行和 staging 文件；不删除已入库知识；UI 文案为“删除任务记录”。
  - `action=retry_failed`：把失败文件重置为 `queued`，重新入队；重复文件仍按去重跳过。
  - 返回逐任务结果（成功/跳过/失败），支持部分成功；写审计和轨迹。
- 导入页：
  - 最近任务列表增加复选框、全选、批量操作栏。
  - 任务行主标题显示“首个文件名 + 共 N 个文件”，不再以 `J...` 为主。
  - 展开详情显示逐文件状态、文档/草稿链接、重复原因、错误。
  - 回退前弹出预览：本批将停用 N 个文档、退回 M 个草稿；若文档在导入后被修改，提示“修订链保留，停用后可恢复”。
  - 旧任务回退按钮 disabled，tooltip 说明原因。

**验收**

- 同一文件导入两次：第二次任务 `skipped`，文档/草稿总数不变。
- 同一批次内重复文件：只入库一次。
- CSV 一行多文档：文件行 `doc_ids` 包含全部 ID；回退停用全部。
- 回退后可恢复：文档详情“启用”恢复检索；草稿不再出现在待入库。
- 删除任务记录不影响已入库文档；旧任务回退不可用但可删除记录。

### WP4 知识库执行轨迹（P0，3 人日）

对应你的 2e。

**接入方式**

- `App` 初始化顺序调整：先创建 `TraceStore`，再创建 `KBService`/`ReviewService`；或创建后注入 `kb.traces`。`TraceStore` 只依赖 `db/config`，不依赖 KB。
- 统一 `kind="kb"`，`meta.action` 区分：
  - `import`：`ref_id=job_id`
  - `review`：`ref_id=review_id`
  - `query`：`ref_id=query_id`
  - `library_backup` / `library_restore`：`ref_id=library_id` 或备份任务 ID
- 事件：
  - 导入：`stage`（接收/解析/查重/建文档/建草稿/索引）、`validation`（文件大小/格式/重复）、`error`（单文件失败）、`run_end`（completed/partial/failed/cancelled）。
  - 审核：`stage`（加载目标/规则校验）、`model_request`/`model_response`/`model_error`（复用 `gateway.complete(trace=...)`）、`validation`（规则重算/blocker）、`run_end`。
  - 问答：`stage`（检索/合并/模型）、`model_request`/`model_response`/`model_error`、`run_end`。
  - 备份/恢复：`stage`（打包/校验/写库/重建索引）、`error`、`run_end`。
- 异步导入/审核在 worker 内创建 recorder，`finally` 关闭；轨迹写失败不能影响主流程。
- 同步错误：`KBError` 增加 `trace_id` 字段；`_kb_raise` 在错误响应中带 `trace_id`（仅管理员可见链接）。异步失败：任务/审核详情按 `ref_id` 查轨迹。
- `GET /api/traces?kind=kb&ref_id=...` 复用现有 API；`_trace_public` 增加 `kb` 类型：
  - `import`：显示任务名称（首个文件名 + 文件数）；
  - `review`：显示审核对象标题；
  - `query`：显示问题文本；
  - `library_*`：显示库名。
- `page_traces.js` 的 `KIND_LABELS` 增加 `kb: '知识库'`；列表按 `meta.action` 显示子类型。
- 知识库页面：
  - 导入任务详情、审核详情、问答错误横幅增加“查看执行轨迹”链接（管理员可见）。
  - 非管理员错误只显示“请联系管理员并提供轨迹 ID”，不暴露轨迹内容。
- 轨迹保留沿用 `trace_retention_days`、`trace_max_*`；模型请求中的原文只对管理员可见，和诊断/工坊一致。

**验收**

- 一次导入、一次审核、一次问答分别产生一条 `kind=kb` 轨迹，`ref_id` 正确。
- 失败导入/审核轨迹含 `error`/`model_error`，能从页面跳到 `#/traces/{id}`。
- 单文件失败不阻断其他文件；轨迹 `run_end` 为 partial。
- 轨迹关闭（`trace_enabled=false`）时 KB 功能不受影响。

## 6. 迁移步骤

   - 增加列/表；回填 `kb_id=1`；
   - 创建 `kb_library_index_meta`，从旧 `kb_index_meta` 复制库 1 元数据；
   - 回填 `kb_cases.kb_id`、`kb_documents.content_sha256`（可按需异步）；

3. 重建库 1 索引；校验 `doc_count/case_count/checksum`。

按 4 条线并行（状态/审核、导入/前端、多库/索引、测试/交付）可压到约 3 周；单人顺序推进按 5–6 周预估。不要按原文档的 15.5 人日排，因为原文档没有包含多库、跨库、备份迁移、轨迹和批量导入。

### 8.2 主要风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 多库过滤遗漏 | 跨库串数据，最严重 | 服务层统一 `kb_id` 参数；SQL 审查；每库隔离测试；禁止 API 直接拼 SQL |
| 单库排序回归 | 旧用户感觉检索变差 | 单库走原 `retrieve`；跨库才 RRF；基线对比 |
| 去重误杀 | 合法同内容文档被跳过 | 仅精确 SHA-256；管理员“强制导入”；跳过原因可见 |
| 回退误停用人工修改文档 | 用户数据被隐藏 | 回退前预览名称；保留版本/修订；可恢复；审计 |
| 旧任务无关联 | 用户以为能回退 | 迁移标记 `rollback_supported=false`；UI 明确说明 |
| 审核批量误操作 | 大量错误发布 | 二次确认；服务端逐项校验 blocker；批量结果逐项可见；可审计 |
| 模型 fallback 改变审核行为 | 审核结果与旧版不同 | 记录 model_decision/model_score；规则重算；对比测试 |
| 备份包过大/路径穿越 | 磁盘/安全 | 大小上限、流式校验、zip 路径白名单、manifest 校验 |
| 轨迹泄露原文 | 隐私 | 仅管理员；沿用 trace 权限/保留策略；错误页只给管理员链接 |
| 默认库误删 | 平台不可用 | 默认库禁止删除；先切换默认；删除前强制备份提示 |

### 8.3 回滚原则

- 代码回滚：1.31.0 之前保留 1.30.5 离线包；DB 新列/新表 additive，旧代码可忽略。
- 数据回滚：迁移前备份 DB + `data/kb`；恢复后重跑库 1 索引。
- 功能开关：多库、跨库检索、批量回退、轨迹分别加配置开关；默认开启前先灰度验证。
- 删除库只做归档，不做不可逆物理删除；物理清理走离线脚本。
