# 诊断推理数据说明

本目录说明平台如何把“资深工程师的排查思路”变成**可执行、可回归、可审计**的数据，而不是让模型自由生成一段思维链。

## 1. 数据分层

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 规则与证据 | `fault-profile.yaml` 的 `analysis.steps` | 真正决定命中的正则、路径、阈值和根因条件 |
| 诊断推理 | `fault-profile.yaml` 的 `diagnostic_reasoning` | 竞争假设、检查顺序、鉴别点、误判陷阱、停止条件 |
| 技能目录摘要 | `Skill.catalog_entry()` 的 `diagnostic_reasoning` | 给 planner 形成假设、选择最少技能 |
| 任务报告 | `## 三、研判路径` | 按真实命中/未命中显示假设成立、排除或证据不足 |
| 案例与语料 | `cases/`、`datasets/diagnostic_reasoning/` | 回归、检索基准、planner/报告语料 |
| 种子经验 | `knowledge/reasoning_playbooks.json` | 随包分发，启动时写入 `plan_experiences`，标记 `curated_reasoning` |

关键约束：推理中的规则编号必须真实存在；报告只陈述本次实际命中和未命中，不用“未命中的规则”编造排除理由，也不把种子经验当成本次结论。

## 2. 案例规模

当前共 75 条合成案例：

| 技能 | 案例 | 正例 | 反例 | 边界 | 根因分布 |
| --- | ---: | ---: | ---: | ---: | --- |
| `bbu-fault-vsw-watchdog` | 25 | 20 | 4 | 1 | R1 8 / R2 6 / R3 6 / NONE 5 |
| `bbu-fault-vsw-ssd` | 26 | 21 | 2 | 3 | R1 7 / R2 5 / R3 6 / R4 3 / NONE 5 |
| `bbu-fault-vsw-usbflash` | 24 | 18 | 4 | 2 | R1 8 / R2 7 / R3 3 / NONE 6 |

覆盖维度：
- 全根因：每条根因条件至少 3 条正例；
- 阴性/边界：`protect_status=0`、`Remain Life=30`、扇区计数 0、只看 SATA link down、MCE 但无 Simplelog 等；
- 组合证据：MCE+caterr、MCE+电源、caterr+电源、I/O+寿命、寿命+扇区等优先级；
- 路径/采集：深层站点目录、文件名变体、zip、tar.gz、嵌套 zip；
- 断言：`case.yaml` 是唯一来源，包含 `hit_rules`、`not_hit_rules`、`root_cause`，回归脚本直接消费。

## 3. 推理数据结构

```yaml
diagnostic_reasoning:
  strategy: 先查什么、再查什么、什么证据优先
  decision_order:
    - order: 1
      action: 来自原始资料的判断步骤
      rule_ids: [E1]
      if_hit: 命中后如何收敛
      if_miss: 未命中时不得反推根因
  hypotheses:
    - id: H1
      root_cause: R1
      name: MCE/Kernel panic 导致看门狗复位
      condition: E1 and E2
      supporting_rules: [E1, E2]
      excluding_rules: []
      expected_evidence: [...]
      why: 故障机理
  discriminators:
    - rule_id: E2
      meaning: 内核记录 MCE 或 Kernel panic
      supports: [...]
      excludes: [...]
      use: 先看 E2；命中时优先验证……并排除……
  checks: 阈值与字段口径
  pitfalls: 误判陷阱
  stop_conditions: 何时停止扩根因
  data_needed: 需要哪些日志源
```

这些字段由 `bbu/workshop_spec.py` 的 `_build_reasoning()` 从整段资料、已编译规则和根因条件确定性生成；模型只参与语义提取，不直接写 YAML。

## 4. 平台消费方式

1. **planner**：技能目录携带 `diagnostic_reasoning`，提示词要求先形成 1–3 个竞争假设，再选最少技能；合成历史经验只作为排查路径参考。
2. **报告**：`bbu/reports.py` 用本次 `match_counts` 和根因 `established` 状态生成“研判路径”，显示每条规则命中数、每个假设是采信/排除/证据不足。
3. **经验库**：任务终态仍按原有自动沉淀写入真实结果；`knowledge/reasoning_playbooks.json` 只提供 3 条带 `source=curated_reasoning` 的剧本，明确不预判根因。
4. **回归**：`build_child_skill.py` 跑完 75 条案例与关键端到端报告；`tests/diagnostic_benchmark.py` 再测技能检索 Top-1。

## 5. 验证结果与边界

- 看门狗 25/25、SSD 26/26、USBFLASH 24/24 通过；关键 E2E 分别 7/7、6/6、7/7。
- 75/75 案例技能检索 Top-1 = 100%。
- 平台级任务验收：一条 caterr 案例得到 `R2`，报告出现“研判路径”“总体策略”“关键鉴别点”“条件不成立，排除”，并检索到种子剧本。
- 全部日志为合成数据，不代表真实 C1–C4/USBFLASH/SSD 现网日志已验证；真实日志到位后应补充采集、复核阈值和去误报，不得直接宣称现网命中。
- 当前证据强度仍是规则匹配 + 条件优先级；没有学习真实工程师的隐性经验，后续应把现场确认/否定的结果回写为案例，逐步替换合成样本。
