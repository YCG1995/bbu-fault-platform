# 故障知识库 300 条评测集标注指南（1.33.0）

> 本指南用于把“300 条金标准”从一句目标变成可复核的数据资产。平台负责导入、计算指标和冻结 run；**qrels 必须由专家标注，系统不用模型生成标准答案**。没有专家复核的 qrels 只能当烟雾测试，不能作为上线准确率依据。

## 1. 目标与边界

- 规模：300 条查询，建议四类各 75 条。
- 用途：回答“这个知识库/这次检索改动到底有没有变好”，不是训练模型，也不是自动生成答案。
- 标注对象：查询 + 相关案例 ID（qrels）。qrels 是“检索到哪些案例算正确”的集合，不等同于最终回答文本。
- 数据来源：真实工单、现网故障记录、脱敏后的历史查询、专家现场问题。禁止用 AI 批量生成问题后自己编 qrels；禁止把模型输出当作金标准。
- 隐私：进入评测集前先脱敏姓名、工号、电话、邮箱、客户标识和未公开网络信息；原文只保留在受控知识库，评测文件只放脱敏查询与案例 ID。

## 2. 300 条分布

| 类别 `category` | 条数 | 查询写法 | qrels 口径 |
| --- | --- | --- | --- |
| 实体精确 | 75 | 板卡型号、告警码、版本、部件名，如 `VBPE2 看门狗复位` | 至少 1 个直接对应案例；同根因的多案例可标多个 |
| 症状描述 | 75 | 现场现象描述，如 `单板每 2 分钟复位一次，业务恢复后又断` | 现象/原因匹配的案例；允许 1–3 个等价案例 |
| 口语改写 | 75 | 工程师口头说法、缩写、错别字、方言词，如 `VBP 单板老重启咋整` | 语义等价的案例；不可因为字面不同就标空 |
| 库外无答案 | 75 | 知识库确实没有的问题，如 `红烧肉怎么做`、无关产品问题 | 必须为空 qrels；检索到任何案例都算拒答失败 |

分层建议：

- `split=dev`：前 100 条用于调参和调试，允许反复运行。
- `split=test`：后 200 条冻结，只用于验收和版本对比；不要在看到 test 结果后回去改 qrels。
- 如果现场只能先做 100 条，先按四类各 25 条做第一版，再扩到 300；不要把 100 条拆成 300 条重复项。

## 3. 单条记录格式

JSONL 每行一个对象：

```json
{"query":"VBPE2 单板看门狗复位，业务反复重启","qrels":["K69b3cfb8d7181edd"],"category":"实体精确","split":"test"}
{"query":"单板每两分钟断一次，起来又断","qrels":["K69b3cfb8d7181edd","K3310986b9db557ad"],"category":"症状描述","split":"dev"}
{"query":"红烧肉怎么做","qrels":[],"category":"库外无答案","split":"test"}
```

CSV 等价格式：

```csv
query,qrels,category,split
"VBPE2 单板看门狗复位，业务反复重启","K69b3cfb8d7181edd","实体精确","test"
"红烧肉怎么做","","库外无答案","test"
```

字段约束：

- `query` 必填，去首尾空白，单条建议不超过 200 字。
- `qrels` 是案例 ID 数组；CSV 用英文逗号分隔。案例 ID 必须来自当前目标库的 active 案例。
- `category` 只使用四类中文名；未知类别会被归到“未分类”。
- `split` 只使用 `dev` / `test`；缺省为 `test`。
- 不要放文档 ID、标题或 URL 到 qrels；评测按 `case_id` 计算。

## 4. 标注流程

1. **选库与冻结范围**：确定评测针对哪个 `kb_id`；记录当前文档数、案例数、索引 checksum。跨库评测应拆成单库评测，不要混库。
2. **抽样**：从真实查询日志、工单和专家经验中抽取候选问题；每类先凑 20–25 条做校准集。
3. **双人标注**：一名标注人给出 qrels，另一名复核；分歧记录在标注表，不直接改数据。
4. **裁决**：第三名专家或标注负责人裁决；记录裁决理由（同根因、同现象、同方案、仅相似标题不算）。
5. **冻结**：导出 JSONL/CSV，计算文件 SHA256，记录版本号（如 `golden-300-v1`）、标注人、复核人、日期、目标库 checksum。
6. **导入与运行**：在 `#/kb/docs?tab=eval` 导入，先跑 `dev` 校准，再跑 `test`；每次 run 保存 `metrics_json` 和失败样例。
7. **复盘**：失败样例分为“qrels 标错”“检索没召回”“排序不对”“库外未拒答”四类；只有前一类可以修数据，后三类进入检索/索引改进。

## 5. 运行与验收口径

- 同一冻结索引连续运行两次，Recall@1/5/10、MRR、nDCG、无答案准确率必须一致；不一致先查索引 checksum 和 qrels 是否被改。
- 索引变化后旧 run 只能参考，不能直接对比；页面会标“索引已变化，不可比”。
- 分类别看，不只看总体：实体精确应接近 1.0；口语改写允许低一些；库外无答案看拒答准确率，不看 Recall。
- 建议的上线门槛（需结合现场基线调整）：
  - 实体精确 Recall@5 ≥ 0.90；
  - 症状描述 Recall@5 ≥ 0.80；
  - 口语改写 Recall@5 ≥ 0.65；
  - 库外无答案拒答准确率 ≥ 0.90；
  - MRR@10 不低于上一基线，nDCG@10 不下降；
  - 300 条 run 的 P95 延迟在可接受范围，单条失败有记录。
- 指标不达标时，先看失败样例属于哪一类；不要用生成式模型改 qrels 把数字“修好”。

## 6. 版本与变体

- 每次 qrels 变更都生成新版本，不覆盖旧文件；记录变更原因和影响条数。
- 词典、索引参数、模型提示词变更时，保留旧 run 作为基线；新 run 的 `config_hash`/`prompt_version` 不同，页面会提示不可比。
- 需要对比同义词效果时，固定同一索引和同一 qrels，只改变 `kb_terms`，分别运行并导出 CSV。
- 需要对比多库时，为每个库单独建评测集；跨库 RRF 的评测应另建集合，并明确 qrels 所属库。

## 7. 常见反模式

- 用模型生成 300 条问题，再用模型生成 qrels：这不是金标准，不能用于验收。
- 只标“标题相似”的案例：标题相似但原因/方案不同的负样本会污染指标。
- 把库外问题标一个“最接近”的案例：这会人为压低拒答准确率，也违背库外无答案类定义。
- 看到 test 指标后修改 qrels：test 集失去独立性，只能当 dev 集重新冻结。
- 把 300 条全部放 test：没有校准集，调参时容易过拟合。
- 只跑一次不看失败样例：指标是结果，失败样例才是改进输入。

## 8. 交付清单

- `golden-300-v1.jsonl` 或 `.csv`，含 300 条记录；
- 标注说明：标注人、复核人、裁决人、日期、目标库 `kb_id`、索引 checksum；
- 文件 SHA256 与版本号；
- 至少一次 dev run 和一次 test run 的 `metrics_json`/失败样例导出；
- 一页复盘：达标项、未达标项、失败分类、下一步动作。

平台不会自动生成上述人工交付物；它只保证导入、计算、冻结和导出可复现。
