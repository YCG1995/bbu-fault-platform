# 架构设计

## 1. 设计目标与取舍

平台面向内网 5–20 人、4–8 并发的现场诊断场景，硬约束是**完全离线**。因此没有引入 Web 框架、任务队列、前端构建链或外部数据库：

- 后端：Python 3.12 标准库 `http.server` + 自研 HTTP 路由、SQLite（WAL）、线程池 worker。
- 前端：原生 ES Module + 原生 CSS，无 npm/CDN，静态资源由同一服务进程提供。
- YAML：仅 vendor 纯 Python PyYAML，避免现场 pip。
- AI：只实现 OpenAI 兼容与 Anthropic 原生两类协议，统一抽象为 `AIGateway.complete(role, ...)`。

代价是需要自己维护 HTTP 解析、鉴权与并发边界；收益是拷贝一个目录即可运行，升级不依赖外网。

## 2. 进程与线程模型

```text
                    ┌─────────────────────────────────────────┐
 Browser ──HTTP──▶  │ ThreadingHTTPServer（bbu/httpd.py）      │
                    │  Router / 静态资源 / SSE / 上传解析       │
                    └───────────────┬─────────────────────────┘
                                    │ enqueue
                    ┌───────────────▼─────────────────────────┐
                    │ TaskWorker（bbu/worker.py）              │
                    │  task queue + max_workers 线程池         │
                    │  每个任务一个 TaskPipeline.run()         │
                    └───────────────┬─────────────────────────┘
                                    │ 动态计划
        ┌───────────────────────────▼───────────────────────────┐
        │ TaskPipeline（bbu/pipeline.py）                         │
        │ 受理 → 盘点 → AI 规划 → 波次执行 → 可选补规划 → 仲裁 → 报告
        │                 │                                      │
        │                 ├─ ThreadPoolExecutor(max_skill_parallel)
        │                 │    SkillRunner 子进程（隔离超时/输出上限）
        │                 └─ AIGateway（有界调用，失败回退）       │
        └───────────────────────────────────────────────────────┘

  Worker 完成 → LearningService（bbu/learning.py）后台线程
                  ├─ ExperienceStore.record() 写规划经验
                  └─ 成功任务 → 工坊「自学习」草稿（不自动发布）
```

- 任务级并发由 `max_workers` 控制，默认 4；单任务内技能扇出由 `max_skill_parallel` 控制，默认 4。
- 每个子 Skill 通过 `subprocess` 执行 `scripts/run_analysis.py`，设置独立超时 `skill_timeout_sec`（默认 900s）、输出截断与环境隔离；技能崩溃不会拖垮主进程。
- SSE 每 15 秒发送心跳；任务事件按 `seq` 递增写入 `task_events`，刷新页面可按 `Last-Event-ID` 续传。
- `LearningService` 是独立 daemon 线程 + 有界队列（200），诊断完成不等待沉淀；队列满只记事件，不影响任务结果。

## 3. 动态诊断计划

### 3.1 阶段

1. **受理**：校验任务参数、保存上传日志、创建 `tasks` 记录并入队。
2. **盘点**：调用 `inventory_inputs` 递归解压 zip/tar，识别日志类型、文件名、告警码、时间窗与快速签名；解压受文件数/总大小/目录穿越限制。
3. **AI 规划**：`TaskPipeline._plan()` 优先使用 `planner` 角色模型；老部署只配 `router` 时复用 `router`。没有真实模型、调用失败或计划非法时，回退 `deterministic_plan()`：按规则分选候选，所有候选一波并行。
4. **按计划执行**：`_execute_plan()` 逐波执行；波次内技能用 `ThreadPoolExecutor` 并行，波次之间按 `gate` 决定是否推进。每个技能只执行一次。
5. **可选补规划**：仅当证据不足/无命中/最高置信度非 high/执行缺口时调用一次；补规划只能新增未执行技能，返回空 `steps` 表示停止。
6. **仲裁**：若只有 1 个候选则采信；多个候选结论冲突时最多调用 1 次 LLM；否则按确定性综合分（结论状态 + 证据质量 + 技能匹配分）裁决。
7. **报告**：确定性 Markdown 骨架，可选 1 次 LLM 研判补充「现场判断/建议」，逐条绑定证据编号；同时生成 HTML 报告。报告附录 A 保存 AI 计划，附录 B 保存子技能原始报告。

### 3.2 计划结构与门槛

模型只输出结构化计划，不直接输出根因：

```json
{
  "in_scope": true,
  "summary": "先验证时钟直接证据，未命中再补光路",
  "hypothesis": ["参考时钟源失锁", "光模块收光异常"],
  "steps": [
    {"id": "P1", "title": "时钟首验", "objective": "...",
     "skills": ["demo-bbu-clock-loss"], "gate": "always", "reason": "..."},
    {"id": "P2", "title": "补验光路", "objective": "...",
     "skills": ["demo-bbu-optical-rx"], "gate": "previous_unmatched", "reason": "..."}
  ],
  "missing_info": []
}
```

`normalize_plan()` 的确定性裁剪：

- 只允许技能目录内的技能；目录外、重复、已执行技能直接丢弃；
- 首步（非补规划）强制 `gate=always`；非法 gate 归一为 `always`；
- 单步技能数不超过 `max_skill_parallel`，总技能数不超过 `planner_max_total_skills`，步数不超过 `planner_max_steps`；
- 裁剪后没有可执行技能则返回 fatal error，由编排器回退确定性计划，不再调用模型修复。

`gate_allows()` 在运行期判断：

| gate | 触发条件 |
| --- | --- |
| `always` | 无条件 |
| `previous_unmatched` | 前序至少一个技能未命中/无证据/执行失败 |
| `previous_conflict` | 前序出现多个不同根因，或时序冲突 |
| `previous_low_confidence` | 有命中但最高置信度不是 high，或没有命中 |
| `previous_gap` | 前序存在执行错误、缺组件、glob 兜底或明显局限 |

### 3.3 停止条件

`needs_replan()` 只在以下情况返回 true：

- 没有剩余技能 → false；
- 所有计划技能都没有结果 → true；
- 没有任何技能命中 → true；
- 多个不同根因并存 → false，交给仲裁比较证据，不在这里继续扩搜；
- 唯一匹配根因但最高置信度不是 high → true；
- 唯一高置信根因 → false，停止扩展。

因此整体是「一次规划 + 最多一次补规划 + 一次仲裁 + 一次报告」，不存在由模型决定是否继续调用工具的循环。计划中的技能还受任务级 `Budget`（默认 12 次 LLM 调用 / 200k token / 2400s 墙钟）约束。

## 4. AI 网关与预算

`AIGateway` 统一封装：

- OpenAI 兼容：`POST {base_url}/chat/completions`，`Authorization: Bearer <key>`；支持 `response_format` 不可用时自动降级纯文本。
- Anthropic：`POST {base_url}/v1/messages`，`x-api-key` + `anthropic-version`；解析 `content[].text`。
- Mock：无网络，返回确定性 JSON，用于联调。

角色：

| 角色 | 用途 | 调用上限 |
| --- | --- | --- |
| `planner` | 生成初始动态计划 | 每任务 1 次 |
| `router` | 老部署兼容；没有 planner 时复用 | 每任务 1 次 |
| `arbiter` | 多候选结论冲突时仲裁 | 每任务 1 次 |
| `writer` | 报告综合研判 | 每任务 1 次 |
| `workshop` | 工坊 profile 起草 | 按工坊操作 |

每个任务创建独立 `Budget`：

```text
max_llm_calls     默认 12
max_total_tokens  默认 200000
task_timeout_sec  默认 2400
```

每次调用前 `Budget.check()` 校验调用数与 Token 余量；任务墙钟到点后同样拒绝新调用。连续失败会在网关内熔断，避免坏 endpoint 反复超时。所有 AI 失败路径都必须回退到确定性逻辑，任务仍会产出报告，不会卡死。

## 5. 经验库与自动沉淀

### 5.1 经验库

每次任务到达 `done` 后，`ExperienceStore.record()` 写入 `plan_experiences`：

- `task_id`、技能、根因、置信度、任务终态 `status=done`；
- 现场描述、日志盘点 hints；
- `plan_json`：计划摘要、假设、波次、技能、来源、补规划摘要；
- `outcome_json`：结论状态、采信技能、证据缺口、技能表现、耗时与 LLM 调用数。

下一次规划前，`ExperienceStore.search()` 用「描述 + hints + 技能名」的字面与中文二元组重叠检索最近 200 条，按 `overlap / len(query)` 评分，同一技能和根因命中时加权；结果作为 planner 的参考注入提示词。经验只帮助排序和避坑，不能替代本次证据。

### 5.2 自动沉淀

任务满足以下全部条件时，`LearningService` 后台创建工坊草稿：

- `tasks.status=done`；
- `verdict.status=matched`；
- 置信度 `high` 或 `medium`；
- 有可复用日志包；
- 同一 `source_task_id` 或同一根因尚未有自学习草稿（同根因去重）。

草稿命名 `bbu-fault-learn-<sha1(task_id|root_name|skill_name)[:10]>`，标题「自学习：<根因>」，`category=自学习`，`source_task_id` 记录来源。日志先硬链（失败则复制）到 `data/tmp/learning/<task_id>/`，再调用 `WorkshopService.attach_logs()` 生成规则候选与 profile。**不会自动发布**，必须管理员在工坊确认规则/根因后手动构建、验证、发布。

## 6. 子 Skill 契约与工坊

平台兼容元 Skill `bbu-fault-skill-builder` 生成的标准产物：

```text
<skill>/
  SKILL.md
  assets/fault-profile.yaml
  scripts/run_analysis.py
  scripts/search_evidence.py
  scripts/render_report.py
```

注册时做健康检查：

- `ready`：关键组件齐全；
- `degraded`：缺规则/根因但可执行；
- `incompatible`：缺 `run_analysis.py` 或 profile 等关键组件，绝不静默假装可执行。

工坊流程：

1. 创建草稿，生成确定性 `profile.yaml` 骨架；
2. 上传日志包，递归解压并调用 `scan_rule_candidates.py` 生成规则候选；
3. 配置了 `workshop` 角色模型时，AI 仅起草 profile 文本；失败自动回退骨架；
4. `scaffold_child_skill.py --check` 校验；`build_child_skill.py` 构建，若有案例则跑回归，否则 `--skip-regression` 并标记未验证；
5. 管理员发布：版本归档到 `data/skill_versions/<name>/<version>`，复制到 `skills/`，注册表重扫后参与规划。

元 Skill 有一条硬规则：根因只能引用 `verified: true` 的规则。未验证规则直接构建会被拒绝。平台工坊在失败时给出「标记为已验证并重试」按钮，但要求人工确认并重写 YAML，不会静默放宽规则。

## 7. 数据与安全

SQLite 主要表：

- `users` / `sessions`：账号、scrypt 口令、会话与 CSRF token；
- `model_configs`：协议、Base URL、加密 API Key、角色、优先级；
- `tasks` / `task_skills` / `task_events`：任务、技能结果、SSE 事件；
- `skills` / `skill_versions` / `workshop_drafts` / `cases`：技能生命周期；
- `plan_experiences`：规划经验（schema v2 新增）；
- `audit_logs`：登录、任务、技能、模型、用户、自学习操作留痕。

`workshop_drafts.source_task_id` 在 schema v2 新增，并建部分唯一索引 `idx_drafts_source_task`，保证一个任务只自动沉淀一次；旧库启动时由 `Database.init_schema()` 做幂等迁移。

安全措施：

- 口令 `scrypt` + 随机盐；初始密码文件 `0600`，首次登录强制修改。
- 会话 Cookie `HttpOnly; SameSite=Strict`；所有写接口校验 `X-CSRF`。
- API Key 使用 `data/master.key` 派生密钥加密，密钥文件 `0600`；前端只显示掩码。
- 上传文件安全文件名、大小上限、zip/tar 目录穿越与符号链接拦截、解压炸弹限制。
- CSP 禁止内联脚本与外部资源；报告 iframe 使用 `sandbox`。
- RBAC：admin 可管理模型/用户/审计/技能发布；engineer 可建任务、看自己的任务、编辑自己的工坊草稿。

## 8. 目录与部署形态

开发/单机模式：所有路径相对项目根；`data/` 与 `skills/` 可写。

生产模式（`install_offline.sh`）：

- 代码只读：`/opt/bbu-fault-platform`；
- 数据可写：`/var/lib/bbu-fault-platform/{data,skills,cases}`；
- `config.json` 使用绝对路径；
- systemd `ProtectSystem=strict`，仅 `ReadWritePaths` 放开数据目录；
- 前端、vendor、meta 全部随包，运行时不访问外网。

## 9. 已知边界

- 单机 SQLite + 线程模型适合 5–20 人；若扩展到多节点，需要外置数据库与共享存储，当前版本不支持横向扩展。
- SSE 为进程内广播，服务重启后进行中的任务会失败；重启后需重新提交（历史结果保留）。
- 计划来自模型时仍可能出现“选错方向”的合理错误；平台只能保证技能目录、预算、重复执行和循环边界，不能保证诊断正确。最终以技能证据链与现场复核为准。
- 自动沉淀只做“草稿”，不自动发布；同根因去重后仍可能需要人工合并不同现场表现。
- 平台不执行日志中的任何命令；子 Skill 脚本以低权限服务用户运行，但仍建议在容器/受限账号中部署。
- AI 输出只作为辅助研判，最终处置必须结合现网规程与厂家文档。
