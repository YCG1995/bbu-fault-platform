# BBU 故障诊断平台：开发优化计划（2026-11-27）

> 基线：`1.24.8` / schema `21` / HEAD `08b6c88`  
> 审计依据：三份用户指南 + 当前 `main` 源码 + `feat/general-skill-builder` / `feat/p1-format-rules` 分支 + 实际测试结果  
> 核心原则：先证明“现在到底有什么”，再排期；所有能力项必须落到可执行测试，不以文档描述代替代码事实。

## 0. 结论摘要

1. **三份指南不能直接当作当前现状使用。** 第一、第二份写的是 `1.24.6`，当前已经是 `1.24.8`；第二份的 P0-2“缺统一重试入口”已经过时，`bbu/ai.py::complete()` 已实现 JSON Schema 校验失败后的单次修复。
2. **真正的诊断正确性缺口仍然集中在 O1/O2/O3。** 当前代码没有逐文件量词、站点作用域结论、关联键贯穿布尔根因判定；“站点 A 命中 E1、站点 B 命中 E2，`E1 and E2` 仍成立”的问题依然存在。
3. **第三份报告不是“已合并到当前平台”。** 它对应的实现位于本地分支 `feat/p1-format-rules`（`a70657f`，父提交 `a2ce3b2`），当前 `main` 没有 `record_delta`、格式策略、判别力门禁、CloudMAT 开关和 VSW 12 例。
4. **但该分支不是空头报告，合并成本比重新实现低。** 我在临时 worktree 做了合并预演：相对 `main` 只有 `bbu/skills.py` 一处冲突；解决后、并补齐生成后的 `skills/`，全量 pytest **228 passed**，元技能 selftest **307/307 passed**。干净 checkout 因缺 `skills/` 会失败 3 项，属于测试底座问题，不是业务回归。
5. **当前 REST 冒烟不是“全接口”。** 路由注册表共 **162** 条，`tests/api_full_smoke.py::EXPECTED_ROUTES` 只有 **153** 条，漏了 9 条（8 条迁移接口 + `POST /api/workshop/drafts/{id}/rules/try`）。“153/153”不能作为全接口验收结论。
6. **UI 也没有全按钮门禁。** 静态清点：**98 个 `data-act` 动作名、252 个动作实例、18 个表单、28 处弹窗调用、211 个静态 `<button>` 标签、19 个页面/屏幕**；现有 UI 冒烟显式出现 `data-act` 的只有 15 个动作名左右，远未覆盖全部。
7. **计划顺序：先补测试底座和安全热修，再合并已验证分支，再做规则正确性，最后做工坊/评测/检索/Agent/运维。** 不建议先重写 `record_delta` 或格式策略，也不建议在 O1/O2/O3 未落地前先做 P1 Agent 循环。

### 2.2 已真正提升能力 / 没有提升能力

**当前 `main` 上真正已生效、且对能力有帮助的：**

1. **P0-2 结构化输出单次修复**：它不提升“诊断推理上限”，但显著降低 JSON 解析失败导致的整条任务失败；这是当前最确定的可靠性收益。
2. **O4 的构建期覆盖检查**：`run_regression.py` 已能阻止“根因没有正例/条件规则完全没覆盖”的技能进入构建产物；这是发布安全收益，不是诊断收益。
3. **1.24.8 模型配置平台预设/模型发现**：降低模型接入配置错误，属于可用性收益，不是诊断准确率收益。
4. 现有证据质量分、HypothesisState、工具契约、轨迹、评测框架：这些是平台底座，不在这三份指南的“新增能力”里，但后续 O1/O2/O3 必须复用它们。

**没有提升当前诊断能力、不能计入验收的：**

- O1/O2/O3：核心正确性没有落地。
- O5/O6/O7：规则作者看不到覆盖与语义错误，证据质量不能按来源硬降级。
- O8/P1-2：检索仍是哈希+字面。
- P0-1：工坊 AI 基本看不到上传日志的异常摘要。
- P0-3：评测没有 CI 门禁，3 条 golden 不足以证明稳定。
- P1-1/P1-3：Agent 循环与技能渐进披露未落地。
- O9/O10/O11：运维/治理能力未闭环。
- 三份报告中的 P1 能力：只在分支，不在 `main`；当前用户使用 1.24.8 时享受不到。

### 2.3 文档与代码的三处关键偏差

1. **REST 覆盖率偏差**：文档/汇报里的 153 条不是全量，实际 162 条。当前 `api_full_smoke.py` 漏 9 条，其中迁移 8 条、工坊试跑 1 条。
2. **P0-2 偏差**：第二份指南说“缺统一重试入口”，但 `complete()` 已经有修复逻辑；计划应改为“核验所有调用点 + 补失败注入测试”，不是重新实现。
3. **P1 分支偏差**：第三份报告说“已实现/307 项 selftest/VSW 12/12”，但这是 `feat/p1-format-rules` 分支的事实，不是 `main` 的事实；且报告自己的 195/3 failed 与“干净 checkout 缺 `skills/`”一致，必须先修测试底座。

## 3. 开发优化计划

### 3.1 排序原则

1. **先锁测试底座，再改行为。** 没有 162 路由清单、参数清单、UI 动作清单，任何“全量测试”都是口号。
2. **先修安全，再做功能。** 1.24.8 新增的模型发现是管理员出站请求，当前只校验 `http/https`，没有私网/重定向/响应体上限保护。
3. **先合并已验证分支，再写新规则。** `feat/p1-format-rules` 已经有 `record_delta`、格式策略、判别力门禁、CloudMAT 开关；重写会制造两套实现。
4. **先修诊断正确性，再做工坊/检索/Agent。** O1/O2/O3 直接影响“根因结论对不对”；P0-1 影响“技能生成得好不好”；前者优先。
5. **先做可回退的 shadow，再切 on。** O1/O2/O3 会改变历史 profile 的判定，必须先影子对比，再按案例门禁切换。

### 3.5 R2：1.26.0 规则正确性（12–15 天）

这是本轮最重要的诊断能力提升。所有改动都通过 `rule_scope_v2` 影子开关上线，默认 `shadow`，验收通过后切 `on`。

#### 3.5.1 O1 逐文件量词

**Profile 字段**：

```yaml
rules:
  - id: E1
    type: text
    globs: ["**/clockstatuslog*.txt"]
    any_of: ["CLK032", "PLL unlock"]
    min_matches: 1        # 每个命中文件内的最少命中数
    min_files: 2          # at_least 模式下要求的最少命中文件数
    file_scope: at_least  # any | at_least | each
```

**语义**：

- `any`：兼容旧行为，`hits_total >= min_matches`。
- `at_least`：至少有 `min_files` 个不同文件各自 `>= min_matches`。
- `each`：所有 eligible 文件（glob 命中且可读/可解码）都必须 `>= min_matches`；`min_files` 只能为 0 或不超过 eligible 数，否则 lint error。
- `eligible` 不含明确跳过（binary/ciphered/空文件）；跳过文件单独记 `files_skipped`，不混入分母。

**代码**：

- `_prep_rule()` 维护 `hits_by_file: dict[path,int]`、`files_hit:set`、`files_missed:set`、`eligible_files:set`。
- `_final()` 输出 `files_scanned/files_eligible/files_hit/files_missed/hits_by_file/file_coverage/files_skipped/file_scope/min_files`；`hit` 按三种 scope 计算。
- 报告渲染“命中文件 x/y、每文件命中数”；前端规则编辑增加 `min_files/file_scope` 和实时提示。
- `scaffold_child_skill.py`：校验 `min_files>=0`、`file_scope in {any,at_least,each}`、`each` 与 `min_files` 一致性；导出/模板/示例同步。
- `run_regression.py` 支持 `expected.match_counts` 按文件断言。

**必测真值表**：

| 场景 | 规则 | 结果 |
|---|---|---|
| 5 文件各 1 命中，`min_files=3,file_scope=at_least` | E1 | hit，`files_hit=5` |
| 1 文件 5 命中，`min_files=3` | E1 | miss，`hits_total=5` 但 `files_hit=1` |
| 3 文件各 2 命中，`min_files=3,min_matches=2` | E1 | hit |
| 3 文件各 2 命中，`each,min_matches=2`，另有 1 文件 1 命中 | E1 | miss，指出 1 个文件不足 |
| 只有 binary/ciphered 文件 | E1 | miss，`files_skipped>0`，不伪造 0 文件 |

#### 3.5.2 O2 站点/网元作用域

**Profile 字段**：

```yaml
root_causes:
  - id: R1
    condition: E1 and E2
    scope: site   # all | site | associate
```

**语义**：

- `scope=all`：兼容旧行为，全局求值。
- `scope=site`：按 `site` 分组独立求值；`ALL` 桶（无站点归属）**不计入任何站点分组**，只能用于 `all` 或作为限制项。
- 只有至少一个站点分组成立，根因才成立；`primary` 来自成立的站点分组，不取 `groups["ALL"]`。
- 若 `ALL` 成立但所有站点均不成立，输出 `multi_site_conflict=true`、`status=unmatched`，报告中列“跨站组合不可成立”。
- 单站点/无站点包的旧 profile 不受影响；`scope` 缺省为 `site` 仅对多站点包生效，单站点自动等价 `all`。

**代码**：

- `_group_hit()` 增加 `include_all` 参数；`scope=site` 时 `ALL` 不参与站点分组。
- `eval_verdict()` 返回 `primary_site`、`established_sites`、`multi_site_conflict`、`scope`。
- `report`/`decision_cards` 显示每个站点的一行结论；不再把 `ALL` 主结论冒充站点结论。
- `pipeline` 仲裁：无 `primary_site` 但有 `multi_site_conflict` 时进入 `needs_data`/`unmatched`，不得给出根因。
- 前端工坊/报告显示“站点证据矩阵”。

**必测真值表**：

| 场景 | 规则 | 结果 |
|---|---|---|
| 站点 A 命中 E1，站点 B 命中 E2，`E1 and E2, scope=site` | R1 | 不成立，`multi_site_conflict=true` |
| 站点 A 同时命中 E1/E2，站点 B 无 | R1 | 成立，`primary_site=A` |
| 站点 A 命中 E1，`E2` 只在 `ALL` | R1 | 不成立，`ALL` 不计入 A |
| 单站点包，`scope` 缺省 | R1 | 等价 `all`，旧案例结果不变 |
| 两站点都成立 | R1 | `primary_site` 按 profile 顺序，`established_sites` 列全部 |

#### 3.5.3 O3 关联键贯穿布尔根因

**Profile**：根因 `scope=associate`；规则必须声明同一 `associate_by`（pattern 或 `{site:true}`）；根因内的正规则不得混用不同关联 pattern。

**语义**：

- 以关联键（SN/单板/小区/站点）为独立世界，分别求值 condition。
- 某个键缺规则证据就是该键不成立，不能借 `ALL` 或别的键补。
- `not` 只在该键的局部证据上生效，不跨键。
- 结果输出 `keys_evaluated/keys_established/keys_missing/primary_key`；报告显示每个键的证据矩阵。
- 无关联键的包退回 `site`/`all` 并在 lint 中提示，不静默。

**代码**：

- `_group_hit(result, key)` 支持 `associate` 模式：从 evidence 的 `associate` 字段提取 key；`site` 模式仍走 `site`。
- `eval_condition(expr, hit_ids)` 保持不变，但每个 key 构造独立 `hit_ids` 后调用；新增 `eval_condition_by_key()`。
- `eval_verdict()` 对 `scope=associate` 生成 `keys` 列表并逐个求值；`primary` 只在成立键中取。
- `search_evidence` 证据保留 `associate` 字段；`eval_temporal/trend` 复用同一个 key 空间。
- `scaffold` 校验：`scope=associate` 时每个正规则必须有 `associate_by`；不同 pattern 报 error。

**必测真值表**：

| 场景 | 规则 | 结果 |
|---|---|---|
| SN1 命中 E1，SN2 命中 E2，`E1 and E2` | R1 | 不成立 |
| SN1 同时命中 E1/E2 | R1 | 成立，`primary_key=SN1` |
| SN1 命中 E1，`E2` 无键 | R1 | 不成立，`keys_missing` 列出 |
| SN1 命中 E1，SN1 有 `not E3` | R1 | 按 SN1 局部排除，不受 SN2 的 E3 影响 |
| 两个键都成立 | R1 | 列全部，`primary_key` 按稳定顺序 |

#### 3.6.1 P0-1 工坊日志证据摘要

新增 `bbu/evidence_digest.py`：

**输入**：`extracted/`、配置上限（默认 12k 字符）、日志格式分类、候选规则。

**输出**：

```json
{
  "inventory": {"files": 128, "classes": {"clock": 4, "alarm": 2}, "bytes": 12345678},
  "timeline": [{"minute": "2026-01-01T00:00", "count": 36, "errors": 4}],
  "anomaly_lines": [{"file": "...", "line": 12, "severity": "high", "text": "...", "signature": "..."}],
  "candidates": [{"rule_id": "...", "pattern": "...", "files": 3, "hits": 7}],
  "samples": [{"file": "...", "reason": "high_density", "lines": "..."}],
  "coverage_notes": ["ClockMAT 仅 1 个日志，结构化摘要受限"]
}
```

**算法**：

1. 文件分类与去重：按 `log_format` 分类，统计类型/大小/时间范围。
2. 异常行：正则匹配 `ERROR/FAIL/Exception/timeout/reset/link down/alarm/失锁/驻波/驻波比` 等；按严重度、时间新鲜度、跨文件重复度、模块稀有度打分。
3. 时间线：按分钟/5 分钟聚合，找尖峰；只保留前后各 1 个桶。
4. 候选规则：复用 `scan_rule_candidates`，只保留跨文件出现或高严重度模式。
5. 采样：每类文件最多 2 个样本，优先异常密度高、时间靠近故障、不同模块；不再按文件大小升序。
6. 预算：总字符 ≤ `workshop_egress_max_chars`（当前 12000）；每行 200 字符；超限按分数截断并写 `coverage_notes`。

### 4.5 权限与安全矩阵

| 身份 | 预期 |
|---|---|
| 未登录 | 受保护接口 401；公开接口 200 |
| engineer | 自己的任务/草稿；不能看他人任务、不能管理用户/模型/发布/升级 |
| reviewer | 只看被分配任务与复核；不能模型/用户/发布/升级；模型列表 403 |
| admin | 全部管理；仍需 CSRF；高风险操作确认 |
| 停用/过期 | 401/403，旧会话立即失效 |
| must_change | 只允许 me/password/logout，其余 403 |

安全专项：

1. **IDOR**： engineer 用自己的 Cookie 访问他人 task/case/draft/report/evidence，全部 403；reviewer 只访问被分配任务。
2. **CSRF**：89 个变更路由，缺/错 token 403；GET 不误伤。
3. **XSS**：任务标题、日志行、技能名、报告、审计、通知、案例描述注入 `<img onerror>`/`javascript:`；页面不执行。
4. **SQL 注入**：搜索/筛选/ID 参数注入 `' OR 1=1`；参数化查询，无泄漏。
5. **路径穿越**：上传文件名、备份名、迁移 ID、报告下载、技能名；`../`、绝对路径、符号链接全部拒绝。
6. **Zip 炸弹**：解压比例/文件数/深度/总字节限制；超限 400/413，临时目录清理。
7. **SSRF**：模型发现私网/环回/元数据/重定向/跨主机认证头/1MB 上限。
8. **密钥泄漏**：模型列表、审计、trace、错误响应、导出文件不含 `api_key/master.key/token` 明文。
9. **登录限流**：IP/账号窗口；锁定返回剩余秒数；不泄漏账号是否存在。
10. **MCP token**：只读 token 不能写；写 token 不能 high risk；撤销即失效；远程默认拒绝。

#### 4.6.1 21 个助手工具

1. schema 合法参数 -> 成功；结果字段/类型正确。
2. 缺必填、null、空串、错类型、额外字段 -> 400/错误，不执行副作用。
3. 角色：engineer/reviewer/admin 按 `scope`；越权 403。
4. 风险：`high` 必须二次确认；`medium` 按配置确认；`never` 不可通过 MCP 调用。
5. 大输入/超长字符串/路径穿越/恶意文件名。
6. 重复调用/并发调用：创建诊断只建 1 个任务；删除备份只删 1 次。
7. 审计：每次成功/拒绝都有 trace/audit。
8. 结果脱敏：不返回密钥/其他用户数据。

重点工具：

- `create_skill_diagnosis`：源输入复用、技能选择、重复提交、无权限技能。
- `release_task_storage`：只能释放自己任务；引用中的任务拒绝。
- `delete_backup`：只能删备份，不可删当前/最新；路径穿越。
- `apply_update/rollback_update`：MCP `never`，只能网页+确认。
- `update_user`：不能停用最后一个 admin/自己；角色变更撤会话。
