# BBU FaultScope 1.20.2 版本说明（升级助手 NoNewPrivileges / systemctl 路径修复）

发布日期：2026-11-26

本补丁修复网页离线升级在 systemd 部署下必然失败的问题。1.20.1 的助手工具与 MCP 契约不变，数据库 schema 仍为 **17**，REST 仍为 **146** 条。

## 一、现象

管理员在「系统信息 → 离线升级」执行升级时，页面提示：

```text
无法启动 root 升级助手：sudo: 有效用户 ID 不是 0，/usr/bin/sudo 位于一个
设置了“nosuid”选项的文件系统或没有 root 权限的 NFS 文件系统中吗？
```

这不是升级包损坏，也不是升级助手 Python 代码异常。

修掉 `NoNewPrivileges` 后，部分环境还会暴露第二个独立问题：

```text
无法启动 root 升级助手：/usr/local/bin/bbu-upgrade-helper-trigger:
行 6: /usr/bin/systemctl: 没有那个文件或目录
```

原因是触发器旧版把 `systemctl` 路径写死为 `/usr/bin/systemctl`；部分发行版（如 Ubuntu 16）的 systemctl 实际在 `/bin/systemctl`。

第三个问题是“升级实际成功、版本号已经变了，但网页提示未知错误/连接中断”。旧触发器用同步的 `systemctl start` 等待 oneshot 助手结束；助手执行升级时会停止当前 Web 服务，正在处理升级请求的 HTTP 连接随之被切断，所以页面拿不到成功响应，但后台升级已经完成。

## 二、根因

主服务单元 `/etc/systemd/system/bbu-fault-platform.service` 原先包含：

```ini
NoNewPrivileges=true
```

Linux 的 `NoNewPrivileges` 会禁止进程通过 setuid 二进制获得新权限。平台 Web 进程以 `bbu` 用户运行，需要执行受限的：

```text
sudo -n /usr/local/bin/bbu-upgrade-helper-trigger <job>
```

该链路依赖 `sudo` 的 setuid 位。启用 `NoNewPrivileges=true` 后，setuid 被内核忽略，`sudo` 无法把有效用户 ID 提为 0，于是报出上述错误。即使 `/usr/bin/sudo` 的权限、`sudoers` 和 systemd 都正常，网页升级仍然无法启动。

这与 `nosuid` 挂载的区别是：`ls -l /usr/bin/sudo` 仍显示 `4755 root:root`，但 systemd 服务进程的 `NoNewPrivileges=yes` 阻止了提权。可用以下命令确认：

```bash
systemctl show bbu-fault-platform -p NoNewPrivileges
# 输出 NoNewPrivileges=yes 即命中本问题
```

## 三、修复内容

1. `deploy/bbu-fault-platform.service.in` 不再生成 `NoNewPrivileges=true`。
2. `deploy/oneclick/install.sh` 生成的服务单元同步移除该选项。
3. `deploy/upgrade_offline.sh` 在升级已有安装时，会先备份旧单元、删除 `NoNewPrivileges=true` 并执行 `systemctl daemon-reload`，再启动新版本。
4. `deploy/fix_upgrade_helper.sh` 增加 `NoNewPrivileges` 诊断和 `--fix-nnp`：
   - `--diagnose` 显示服务单元是否启用 NNP；
   - `--fix-nnp` 备份并修改现有单元、重启服务；
   - 如果 systemd drop-in 仍强制启用 NNP，脚本会明确报错，不再误报 sudo 权限问题。
5. 升级失败提示补充排查方向，直接指向 `NoNewPrivileges` 和修复脚本。
6. `deploy/bbu-upgrade-helper-trigger` 不再写死 `/usr/bin/systemctl`：优先用 `command -v systemctl`，再回退 `/usr/bin`、`/bin`、`/usr/sbin`、`/sbin`。
7. `deploy/upgrade_offline.sh` 在升级时同步更新已安装的 `/usr/local/bin/bbu-upgrade-helper-trigger`，避免只换代码不换触发器。
8. 触发器改用 `systemctl --no-block start`：先让 systemd 排队，立即返回；网页拿到 202 后轮询任务状态，不再因助手停服丢掉 HTTP 响应。

权限边界没有放宽为任意 sudo：Web 用户仍只能通过 `/etc/sudoers.d/bbu-upgrade` 执行固定触发器，触发器只接受合法任务 ID 并启动固定 systemd 模板。

## 四、验证

- 用 `setpriv --no-new-privs` 复现：即使 `/usr/bin/sudo` 为 `4755 root:root`，setuid 也被禁用，`sudo` 无法提权。
- 全量 Python：**188 tests，OK**。
- REST 全量冒烟：**146/146**。
- 助手/MCP 契约测试：**7/7**。
- 真实 Chromium UI 冒烟：悬浮助手文档问答/来源、MCP Token 一次性展示、375px 布局通过。
- 1.20.2 Linux 离线包与 Ubuntu16 一键包临时前缀安装，健康检查均返回 `1.20.2`。
- 1.20.1 → 1.20.2 `--no-service` 升级通过；管理员密码哈希、schema 17、settings 和运行数据保留。
- 旧单元迁移函数在隔离 unit 上验证：先备份，再删除 `NoNewPrivileges=true`，调用 `daemon-reload`；新服务模板和 one-click 模板均不再生成该行。
- 用假 `systemctl` 注入 PATH 验证触发器能按 `command -v` 找到，并以 `--no-block start` 启动 `bbu-upgrade-helper@<job>.service`；非法任务 ID 仍返回 2。

## 五、现场修复方式

如果暂时不升级包，可在服务器 root 控制台执行：

```bash
# 先诊断；不要用已经失效的 sudo 启动修复脚本
bash /opt/bbu-fault-platform/deploy/fix_upgrade_helper.sh --diagnose

# 如果 NoNewPrivileges 为 enabled
bash /opt/bbu-fault-platform/deploy/fix_upgrade_helper.sh --fix-nnp

# 如果同时发现 sudo setuid 丢失
bash /opt/bbu-fault-platform/deploy/fix_upgrade_helper.sh --fix-sudo --fix-nnp
```

如果你已经看到“升级后提示未知错误，但版本号已经变了”，说明后台升级实际完成，只是旧的同步触发器把处理请求的 Web 进程一起等停了。不要回滚；先确认健康检查和版本，后续把触发器换成带 `--no-block` 的新版本即可。

如果已经修掉 NNP，但页面改为报 `/usr/bin/systemctl: 没有那个文件或目录`，用 1.20.2 包里的新触发器覆盖旧文件（不需要重启平台）：

```bash
sudo install -m 0755 /tmp/bbu-fault-platform/deploy/bbu-upgrade-helper-trigger \
  /usr/local/bin/bbu-upgrade-helper-trigger
sudo -u bbu sudo -n /usr/local/bin/bbu-upgrade-helper-trigger Utest
```

期望返回“任务 ID 非法”（退出码 2）；然后刷新网页重试升级。

修复后重新生成 read Token 不影响升级助手；直接在网页重试升级即可。若服务器没有 root 控制台，网页自动升级仍不可用，请按 `--manual` 输出的步骤做离线手工升级。

## 六、已知限制

- `NoNewPrivileges=true` 与受限 sudo 升级助手在 Linux 上不可同时成立。本版本选择关闭 NNP，保留 sudoers 固定触发器、`ProtectSystem=strict` 和独立 root helper 作为边界。
- 如果 sudo 所在文件系统确实挂了 `nosuid`/`noexec`，或者当前是禁止 setuid 的容器，`--fix-nnp` 也不能绕过内核限制，只能改挂载/容器配置或 root 手工升级。
- Windows 包仍不启用网页自动升级，保持手动更新流程。
- 构建容器没有运行 systemd，无法执行真实服务 `stop/start` 和完整网页升级链路；目标机升级后需用 `systemctl show bbu-fault-platform -p NoNewPrivileges` 确认输出为 `no`，并补一次网页升级/回滚验收。
