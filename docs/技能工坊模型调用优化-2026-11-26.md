# 技能工坊模型调用优化报告

> 1.19.2 后续：工坊四阶段已改为 OpenAI SSE 流式，并完成看门狗真实四阶段复测；详见 `docs/版本说明-1.19.2.md`。

日期：2026-11-26  
范围：`bbu/workshop.py`、`bbu/workshop_spec.py`、`bbu/ai.py`、`bbu/prompts.py`、工坊前端状态展示  
目标：不改模型，先把模型输入、schema 契约、评审任务和失败回退修好。

## 结论

P0 已落地。核心变化不是“换更强模型”，而是让模型只接收业务字段、只输出当前任务需要的内容，并把失败调用变得可观察。

实测收益：

- 看门狗资料：工坊模型 prompt 从 **46,383 字符降到 16,506 字符**；实际 extract input 从 **15,184 tokens 降到 5,945 tokens**（约 -61%）。
- 公共 spec 29,528 字符，其中 `provenance` 等内部元数据被模型裁剪；`model_spec` 只剩 5,707 字符。
- 通用时钟场景：extract input 从 **5,354 降到 2,666 tokens**；extract、review、repair、review-final 全链路真实成功，质量分 92。
- 看门狗场景至少一次达到 extract + review + repair 成功；因上游 30 秒断连，review-final 仍失败，但失败调用现在会记录 stage、延迟、错误类型和估算 input。
- 全量 Python **171/171**、REST **136/136**、工坊十场景 **10/10**、工坊生成 **20/20**、三配方回归全部通过。

## 代码改动

### 1. 模型 prompt 只带业务字段

文件：`bbu/workshop_spec.py`

新增 `model_spec()`：

- 保留 `fault_name/title/summary/domain/symptoms/log_sources/evidence_rules/root_causes/cases/recovery/risks/thresholds` 等业务字段；
- 移除 `provenance`、`diagnostic_reasoning`、`recipe`、`recipe_candidates`、`hard_fields`、`source_revision`、`compiler` 等内部元数据；
- 对嵌套 rules/root_causes 递归移除 `provenance`、`locked`。

文件：`bbu/workshop.py`

`safe_spec()` 从 `public_spec()` 改为 `model_spec()`；`analysis["intake"]` 仍保留完整 `public_spec()`，页面溯源不受影响。

### 2. 结构化输出按能力降级

文件：`bbu/ai.py`

`AIGateway.complete()` 现在按 `ModelCapabilityStore` 选择结构：

- `strict_schema=true`：发送原生 `json_schema/strict`；
- `json_mode=true`、`strict_schema=false`：发送 `response_format={"type":"json_object"}`，本地仍按原 schema 校验；
- `json_mode=false`：不发送 `response_format`，只在 prompt 中要求严格 JSON。

`_call_openai()` 支持 `{"type":"json_object"}`，不会再把它二次包装成非法的 strict schema。

这样普通 OpenAI 兼容端点不会被强制把可选字段全部变必填，也减少了一类 400/503。

### 3. 评审和修复拆小

文件：`bbu/workshop.py`、`bbu/prompts.py`

- 首次评审 `max_tokens` 从 8,000 降到 **5,000**；实测 4k 会在复杂配方上截断。
- 新增 `workshop_review_final_user()`：修复后的复核只带“上一轮 error + 修复后 spec + 确定性质量”，不再重复整段原文；`review-final` 输出上限 **3,000**。
- 评审 prompt 明确“最多 6 个最重要问题、不重复、不重写完整规格”。

### 4. 失败回退不再丢评审结论

文件：`bbu/workshop.py`

修复了原来的缺陷：

```python
# 修复前：修复失败时无条件重置
quality = audit_spec(spec)

# 修复后：已有 review 时保留评审 error
quality = self._merge_review(audit_spec(spec), review) if review else audit_spec(spec)
```

这样“评审发现 error → 修复调用失败”不会把 error 丢掉，也不会在证据已确认的场景误放行。

### 5. 失败调用可观察

文件：`bbu/ai.py`、`bbu/workshop.py`

`AIGateway.complete()` 新增 `stage` 和 `attempt_sink`：

- 每次成功/失败调用都记录 `stage/model/latency_ms/status`；
- 有 usage 时记录真实 `input_tokens/output_tokens`；
- 无 usage 的网络失败记录 `estimated_input_tokens`；
- HTTP 错误解析 `http_status`；
- 工坊 `analysis["attempts"]` 不再只有成功调用。

同时新增：

- `extract_status`
- `review_status`
- `repair_status`

原有 `ai_status` 保留兼容，前端对 `success + review failed/repair failed` 显示“AI 提取成功，评审/修复未完成”，不再笼统显示“AI 提取成功”。

## 真实模型验证

使用主库 `deepseek-flash`，工坊草稿仍在临时目录，密钥未复制。

| 场景 | 优化后输入 | 结果 |
|---|---:|---|
| 看门狗 | extract 5,945 tokens | 一次 run 达到 extract + review + repair 成功；review-final 被上游 30 秒断连打断；attempts 完整记录 |
| 通用时钟 | extract 2,666 tokens | extract + review + repair + review-final 全成功，质量分 92；因证据未验证仍 `needs_confirmation` |
| USB FLASH | extract 未拿到响应 | 3 次 30 秒 `IncompleteRead`，已回退确定性规则；这是 endpoint 断连，不是 schema 解析错误 |

通用时钟的完整链路说明 P0 的方向正确：同样的模型，在上下文从 5k 降到 2.6k 后，能够稳定完成提取、评审、修复和最终复核。

## 仍未解决

- `deepseek-flash` 端点仍会在约 30 秒时返回 `IncompleteRead` 或 HTTP 503；这不是本轮 prompt 能完全消除的，属于 endpoint 稳定性问题。
- 复杂配方的 `review-final` 仍可能在 30 秒断连；当前策略是保留评审结论、质量门禁不放行，由人工确认。
- 本轮没有做多模型 failover、真实模型探针脚本和完整发布；这些属于 P1。
- 本轮没有把 AI 生成技能直接发布；三个场景都因 E1–E4 未验证停在人工确认，符合现有证据门禁。
