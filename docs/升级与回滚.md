# 平台升级与回滚（离线）

> 以后每次代码修改完成后，交付物是 `bbu-fault-platform-X.Y.Z-offline.tar.gz` 和同名 `.sha256`。已部署服务器不需要重新安装，也不要使用 `install_offline.sh --force` 升级。
>
> 当前版本 **1.24.1**（用量统计 + 用户每日用量图表）。1.24.0 → 1.24.1 不改变 schema（保持 21）；升级前请先备份。

## 1. 标准升级命令

以下以 `1.19.0` 为例，实际替换为收到的版本号。服务器需要有足够磁盘空间存放升级快照。

```bash
# 1) 上传 tar.gz 和 .sha256 到服务器同一目录，先校验
sha256sum -c bbu-fault-platform-1.19.0-offline.tar.gz.sha256

# 2) 解压到新目录；不要在 /opt/bbu-fault-platform 内解压
mkdir -p /tmp/bbu-release-1.19.0
tar -xzf bbu-fault-platform-1.19.0-offline.tar.gz -C /tmp/bbu-release-1.19.0

# 3) 从“新包”执行升级；默认读取现有 config.json 推导数据目录
sudo bash /tmp/bbu-release-1.19.0/bbu-fault-platform/deploy/upgrade_offline.sh
```

标准路径为：

- 程序：`/opt/bbu-fault-platform`
- 数据：`/var/lib/bbu-fault-platform`
- 服务：`bbu-fault-platform`
- 运行账号：`bbu`

自定义过路径时，显式传入：

```bash
sudo bash /tmp/bbu-release-1.19.0/bbu-fault-platform/deploy/upgrade_offline.sh \
  --prefix /opt/bbu-fault-platform \
  --state-dir /var/lib/bbu-fault-platform \
  --service bbu-fault-platform \
  --user bbu
```

## 2. 脚本自动做什么

1. 检查新包完整性、Python 版本和现有安装；
2. 停止 systemd 服务，进入维护窗口；
3. 用 SQLite Backup API 备份数据库，并打包数据、技能、案例、旧代码和 `config.json`；备份归档默认排除原始上传、案例输入和解压目录；
4. 只替换程序代码，保留现有配置和运行数据；
5. 执行 `run.py --init-only`，运行幂等建表与数据库迁移；
6. 重启服务，轮询 `/api/health`，同时校验返回版本必须等于新版本；
7. 打印升级快照位置与回滚命令。

升级期间会停服；日志越大，备份时间越长。请安排维护窗口。

| 内容 | 升级后 |
|---|---|
| `config.json` 自定义配置 | 保留，不会被 `--force` 覆盖 |
| 用户、模型配置、任务、审计、复核记录 | 保留在 SQLite，并自动迁移 |
| `data/master.key` | 保留，模型 Key 仍可解密 |
| 上传日志、真实案例、技能、案例 | 保留 |
| `/opt/...` 下的旧程序代码 | 替换；旧代码保存在升级快照 |

**不要直接修改 `/opt/bbu-fault-platform` 下的代码。** 代码改动应进入源码和下一个发布包，否则升级时会被覆盖。

## 3. 升级后确认

```bash
curl -s http://127.0.0.1:8080/api/health
# 应返回：{"ok": true, "version": "1.24.1"}

sudo systemctl status bbu-fault-platform
sudo journalctl -u bbu-fault-platform -n 100 --no-pager
```

再登录页面确认：旧用户可登录、历史任务和模型配置仍在、技能状态正常、新建任务可完成。

升级快照默认位于：

```text
/var/lib/bbu-fault-platform/backups/<时间>-<旧版本>-to-<新版本>-<PID>/
├── backup.json      # 原路径、版本、服务和健康检查信息
├── code.tar.gz      # 旧代码 + 旧 config.json
└── state.tar.gz     # 数据库一致性快照 + master.key + 数据/技能/案例
```

快照包含密钥和现场数据，按敏感介质管理；确认稳定后可按单位备份策略归档或清理。

## 4. 回滚

### 完整回滚（推荐，尤其跨数据库 schema）

```bash
sudo bash /opt/bbu-fault-platform/deploy/rollback_offline.sh \
  --backup /var/lib/bbu-fault-platform/backups/<升级快照目录> \
  --with-state
```

它会恢复旧代码、旧配置和升级前数据，再把服务切回旧版本并做健康检查。当前数据不会直接删除，而是移到：

```text
/var/lib/bbu-fault-platform/rollback-safety/<时间>-from-<版本>/
```

注意：`--with-state` 会让平台回到升级前的数据时点，升级后新增的任务、复核和案例不再出现在当前库中；它们仍保存在 `rollback-safety`。

### 只回滚代码

仅在确认数据库 schema 与旧代码兼容时，省略 `--with-state`：

```bash
sudo bash /opt/bbu-fault-platform/deploy/rollback_offline.sh \
  --backup /var/lib/bbu-fault-platform/backups/<升级快照目录>
```

跨 schema 或不确定时不要使用代码单独回滚。

## 5. 手工进程部署（无 systemd）

先手工停止原进程，再执行：

```bash
bash /tmp/bbu-release-1.19.0/bbu-fault-platform/deploy/upgrade_offline.sh \
  --prefix /path/to/install \
  --state-dir /path/to/state \
  --no-service
```

脚本完成代码替换和数据库迁移后，用原命令启动服务。`--no-service` 不会替你停止或启动进程。

## 6. 升级失败怎么处理

- 换码前失败：脚本会尝试重新启动旧服务，运行数据未改。
- 换码后迁移或健康检查失败：不要盲目重复执行；先保存脚本输出的快照目录和日志。
- 查看日志：`sudo journalctl -u bbu-fault-platform -n 200 --no-pager`。
- 需要回退时执行上面的完整回滚命令。
- 仍需分析时，生成现场支持包并附上升级快照中的 `backup.json`；不要直接回传 `master.key` 或整份数据库。

升级脚本支持同版本重新部署，用于代码修复；即使版本号相同，也会执行备份、迁移与健康检查。

## 6. 网页上传升级（R4）

网页升级不是替代离线脚本，而是通过固定 root/systemd 助手调用同一套 `upgrade_offline.sh`。主 Web 进程仍以 `bbu` 用户运行，不获得任意 sudo。

### 6.1 一次性安装 root 助手

在服务器上以 root 执行：

```bash
sudo bash /opt/bbu-fault-platform/deploy/install_upgrade_helper.sh   --prefix /opt/bbu-fault-platform   --state-dir /var/lib/bbu-fault-platform   --service bbu-fault-platform   --user bbu --port 8080
```

安装内容：

- `/etc/systemd/system/bbu-upgrade-helper@.service`：root 一次性模板服务；
- `/usr/local/bin/bbu-upgrade-helper-trigger`：只接受任务 ID 并启动固定模板；
- `/etc/sudoers.d/bbu-upgrade`：只允许 `bbu` 执行该触发器；
- `/etc/bbu-upgrade.json`：固定 prefix/state/service/health URL。

验证安装：

```bash
sudo systemctl daemon-reload
sudo -u bbu sudo -n /usr/local/bin/bbu-upgrade-helper-trigger Utest  # 应返回任务 ID 非法
```

### 6.2 网页流程

1. 管理员进入“系统信息 → 离线升级”，选择 `.tar.gz`；
2. 服务端计算 SHA256、校验结构/版本/路径，解压到 `STATE_DIR/updates/<job>/release`；
3. 页面显示目标版本、SHA、大小、版本说明和磁盘/运行任务检查；
4. 点击“执行升级”，重新输入管理员密码；root 助手在独立 systemd 单元中备份、停服、迁移、替换代码、重启并检查健康版本；
5. 浏览器轮询状态，服务重启期间自动重试；刷新页面可恢复状态；
6. 成功后显示“刷新页面”；任意失败/成功记录都有回滚入口。

### 6.3 安全边界

- 只接受管理员 + CSRF + 二次密码；所有提交写审计。
- 只接受 `.tar.gz`；拒绝绝对路径、`..`、符号链接/硬链接、设备文件和异常顶层目录。
- 上传后服务端计算 SHA256；重新预检必须匹配已登记 SHA；root 助手再次校验 SHA 并自行解压，避免使用 Web 可写目录。
- 助手只读 `STATE_DIR/updates/<job>/request.json`，只执行固定的升级/回滚脚本；不接受任意命令或任意路径。
- 升级时默认阻止有排队/运行任务、磁盘不足或已有执行中的任务（409）。
- 状态写入 `STATE_DIR/updates/<job>/status.json` 与 `helper.log`，刷新/重启后可恢复。

### 6.4 工作目录切换与迁移恢复（1.10.0）

root 助手现在也处理两类维护任务，仍使用同一 `bbu-upgrade-helper@.service` 和 `U` 前缀任务目录：

| 动作 | 触发入口 | 助手行为 |
| --- | --- | --- |
| `workspace` | 系统信息 → 切换工作目录 | 停服；复制精简工作区到目标；改写 systemd 的 `BBU_DATA_DIR/BBU_SKILLS_DIR/BBU_CASES_DIR` 与 `ReadWritePaths`；更新 `config.json` 和 `/etc/bbu-upgrade.json` 的 `state_dir`；重启并健康检查 |
| `restore` | 系统信息 → 覆盖恢复 | 停服；校验迁移工作区；把当前 `data/skills/cases` 移到 `backups/import-<任务ID>`；替换为迁移包内容；chown 后重启并健康检查；失败反向恢复 |

目标路径必须在 `/etc/bbu-upgrade.json` 的 `allowed_work_roots` 内，默认是 `/var/lib`、`/srv`、`/data`、`/mnt`。自定义状态目录不在这些根下时，先编辑该字段再提交。

**升级和迁移不是一回事**：

- 离线升级/网页升级是替换程序代码，保留当前数据，失败用升级快照回滚；
- 迁移导出是生成精简业务数据包，用于另一实例或灾备重建，不包含原始上传、案例输入和解压目录；
- 迁移导入是覆盖式恢复，不做增量合并，当前数据备份到 `backups/import-<任务ID>`；
- `upgrade_offline.sh --skip-backup` 产生的快照不能当迁移包，也不能用于迁移恢复后的自动回滚。

迁移包为 ChaCha20-Poly1305 认证加密，目标实例无需 `cryptography`；口令与包应分开传递。恢复后历史任务报告仍可查看，但重跑、案例回流和依赖原始输入的评测会停用。

### 6.5 故障处理

- 上传/预检失败：原包不执行，修复包或重新上传；失败包保留状态用于审计。
- 助手启动失败：检查 `systemctl status bbu-upgrade-helper@<job>`、`journalctl -u bbu-upgrade-helper@<job>` 与 `/etc/sudoers.d/bbu-upgrade`。
- 升级脚本失败：页面显示 `helper.log` 尾部；使用快照回滚，命令同第 4 节。
- 健康检查超时：助手标记失败，不会宣称成功；用快照回滚。
