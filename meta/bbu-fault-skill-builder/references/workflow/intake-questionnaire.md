# 故障 profile 信息采集

## 用法

对外发给专家填写的表单见 `references/workflow/submission-template.md`；本文件是 agent 的追问口径与验收标准，二者不重复。

先读取用户已有描述、规则和案例，只问缺失或冲突项；一次最多 4 问。能从真实日志直接确认的格式、路径、原文不让用户重复回答，但根因、阈值和处理方案必须由用户或权威资料确认。

**最低交付条件**：1 个可访问正例，含日志、已知根因和预期证据。没有正例时只形成访谈记录或候选 profile。

## 必收字段

| 分组 | 必须确认的内容 | 合格标准 |
|---|---|---|
| 身份与范围 | 故障名、别名、告警码；设备/制式/单板/版本；采集来源；触发场景与排除范围 | 能判断用户描述是否属于本子 Skill；无告警码明确写 `[]` |
| 现象与甄别 | 用户可见现象、影响、时间特征；至少 1 个相似故障及区分依据 | 区分依据能落到日志字段或测试项，不写“看起来不同” |
| 证据规则 | 文件 glob、格式/编码、原文关键字或正则、AND/OR/NOT、命中次数、上下文；必要时的关联键、时间格式、时序间隔、数值阈值 | 每条规则可在案例中回放；命中行本身必须代表异常，不能把正常值当故障 |
| 根因与机理 | 每个根因的 ID、名称、`condition`、`confidence`、`mechanism` | condition 只引用已验证规则；`mechanism` 用大白话解释“为什么会导致该现象” |
| 处理方案 | 每个根因的动作顺序、前提、风险、回退、恢复验证、升级路径 | 动作由用户/专家确认；恢复验证写明观察对象和合格标准 |
| 案例 | 正例；尽量补反例和边界例；各案例的预期根因、命中/不命中规则、关键原文 | 路径断言用后缀，不断言绝对路径或行号；共现故障不当作排除条件 |

## 高价值追问

按缺口选择，不要整表照搬：

1. **证据**：“您首先打开哪个文件？请贴一条能确定异常的真实原文。看到 A/B 时分别说明什么？”
2. **阈值**：“具体数值、持续次数和时间窗是多少？来源是规范、告警手册还是案例实测？适用哪个版本？”
3. **时序与归属**：“两个事件谁先谁后，允许间隔多久？多网元时按哪个目录或字段防止串证？”
4. **根因机理**：“为什么这些证据能推出该根因？它怎样导致用户看到的现象？”
5. **处置**：“第一步做什么？有什么风险，如何回退？处理后看哪个指标、观察多久才算恢复？”
6. **反例**：“有没有现象相似但最终根因不同的案例？两者第一条可检索差异是什么？”

## 特殊数据

- **二进制/密文**：默认不解析。只有用户提供格式、工具和样例时才纳入，否则登记“需专用工具”。
- **时钟数值规则**：确认锁定/失效状态枚举、正常范围、绝对值阈值、冷启动过滤、持续计数及各自来源。
- **多站点**：优先 `associate_by: {site: true}`；时序只能在同站点、同关联键内比较。
- **CloudMAT**：先确认总体失败，再定位失败项和“通过标准”原文；电源等伴随失败不排除相位故障。

## 冻结前检查

- 根因 condition 引用的规则均在正例命中，反例不会误判。
- 每条证据可给出文件、行号和原文；阈值、根因机理、处理方案均有来源。
- `mechanism` 不是重复根因名称，而是可理解的因果解释。
- 规则未命中时不自动宣称正常；日志缺失、未提取、格式不支持必须区分。
- 所有内容已复述并获用户确认；未确认项标 `verified: false` 或“待补充”，不得进入确定性结论。
